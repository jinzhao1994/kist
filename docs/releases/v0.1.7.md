# kist v0.1.7

Take selected content offline, edit locally, and merge changes back into your
self-hosted library. This release also brings unified instance settings,
readable URLs and faster cached previews.

## Changes

- Run a separate local client with a complete synchronized metadata catalog and
  on-demand originals and previews. Retain individual files, file combinations
  or selections across boxes for offline use, including nested pages, Live Photo
  videos and subtitle tracks.
- Import and edit while disconnected. Local operations have durable independent
  identities; synchronization applies them in order, preserves original times,
  and assigns authoritative operation IDs on acceptance. Interrupted transfers
  resume and repeated submissions recover the same receipt.
- Synchronize automatically when only one side has changes. When both sides have
  changed, use **Sync now** to merge compatible operations; conflicts pause the
  queue for review. Local history and the recycle bin include applied offline
  changes before synchronization and support strict undo and restoration.
- Connect one client through another client of the same library. The relay can
  retain and exchange temporary work while the authoritative library is offline.
  Relay custody is shown separately from final library confirmation. Node and
  history checks reject loops, unrelated libraries and unsafe upstream switches.
- Manage persistent settings on both instance types in **Settings**. Settings,
  connection details and independently revocable credentials are consolidated in
  private `kist.toml` files. Sparse configurations use defaults; stale editors
  cannot overwrite newer changes. Credentials support readable notes.
- Apply settings immediately when saved; Linux/macOS services also support SIGHUP
  after file edits. Only the listen address requires restart. Time-zone changes
  do not rewrite recorded timestamps, and projection changes do not rebuild
  existing paths. Browser display preferences remain browser-local; the primary
  color belongs to the instance and is present on the first page render.
- Configure cache age using days, with a default of `180d`, and enter capacities
  such as `32 GB` or `32 GiB`. Eligible cache entries are cleaned at startup and
  hourly. Retained content, active transfers and unconfirmed originals remain
  protected. Storage settings show local original, metadata and preview sizes.
- Browse using readable box and file paths, and copy stable ID-based permanent
  links from the file's **…** menu. Existing ID URLs remain supported. Permanent
  links identify the current object; they are not frozen historical snapshots.
- Cache versioned previews in the browser, including spreadsheet previews, and
  reduce repeated client catalog replay during thumbnail reads. Lists detect
  external writes and refresh after uploads or synchronization. Metadata
  extraction includes file-combination members.

See the [offline guide](../offline-client.md) and [settings guide](../settings.md)
for commands, preparation, synchronization and recovery details. Both guides are
included in binary archives in English and Chinese.

## Upgrade

Stop the old service and other writers before replacing the binary or recreating
its container. Preserve the library directory and refresh browser pages after
startup. Existing v0.1.x libraries upgrade without reinitialization. Schema 8
adds a rebuildable synchronization receipt index in a transaction; existing
original blobs and historical log entries are not rewritten.

Configuration migrates to version 2. Legacy library configuration keeps its
identity and explicit settings; an implicit machine time zone is fixed to an
IANA zone, or migration asks for an explicit zone when it cannot determine one.
Development-client `client.json` / `connection.json` and legacy credential files
are consolidated before their old copies are removed. Existing explicit cache
retention values are preserved. Keep `kist.toml` private because it may contain
an upstream credential. Upgrade the authoritative library and all clients to
this release before using the new synchronization protocol.

Old binaries cannot read configuration version 2, schema 8 or the new sync log
and pending-record formats. Do not downgrade by replacing only the executable
or by rebuilding with an older binary. If older-version rollback is required,
keep a pre-upgrade recovery point and its matching binary. This compatible
forward migration does not require a new full-library backup or blob scrub;
continue normal scheduled backups.

Binary archives cover Linux x86-64, macOS Intel/Apple Silicon and Windows x86-64.
Verify downloads against `SHA256SUMS`. Images support Linux amd64 and arm64 at
`ghcr.io/jinzhao1994/kist:v0.1.7` and `jinzhao1994/kist:v0.1.7`. Binary assets,
versioned images and `latest` promotion complete separately; use registry tags
only after their verification succeeds. Preserve existing mounts, UID/GID,
ports and allowed access URLs when recreating containers.

## Limits

The authoritative library remains the only complete, final archive. Clients
synchronize the complete metadata catalog, not all original bytes. Uncached
content is unavailable offline; external map backgrounds may also be unavailable.
A relay acknowledgment does not establish final library acceptance. Unconfirmed
relay branches must finish with their existing upstream before switching nodes.
This release does not include a native phone app, multi-master synchronization,
or automatic resolution of conflicting changes.

The local service must be running for background synchronization and cache
maintenance. Conflict editors cover supported operation types; other changes can
be discarded and recreated against current data. There is no built-in web login:
use a trusted network or an authenticated reverse proxy. Sync credentials grant
library-wide synchronization access, not file-sharing permissions. Historical
originals remain permanently retained by the authoritative library.
