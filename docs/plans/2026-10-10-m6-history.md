# M6 历史 UI

以设计 2.4、2.5、3.9 与第 7 节为准；GC 与保留期配置不进入 v0.1。

## 交付顺序

1. 操作历史 API：全库、box、文件、组与 action 筛选，按 op ID 分页，读取单条详情，复用持久请求去重与严格撤销。列表不读取 payload。
2. 历史查询：从权威日志全局前缀重放到独立临时 SQLite，再查询 box、文件、tag 与 metadata；读取历史原文件；支持历史状态对比。保留原时间，取消与失败时清理临时资源，不改变工作库或日志。测量重放成本后确定资源边界，不提前加缓存。
3. 中英文 UI：历史列表与详情、可定位的撤销冲突、只读历史 box、文件版本链对比、回收站与严格恢复。历史视图明确标识截止点，不混用当前标签名称或当前文件内容。
4. 验收：跨 box/global tag、导入与删除、撤销及撤销的撤销、metadata、历史只读、无效截止点、请求去重、rebuild 与 deep verify；真实浏览器流程及新增视觉基准。每阶段 make check、commit、push 并检查 Actions。

## 边界

- 撤销是一条新的补偿 op；恢复删除也使用原有原子撤销，不引入部分恢复或批量撤销。
- 文件版本链表示同一 file ID 经历的历史状态；当前没有替换文件内容的命令，不额外发明编辑/覆盖语义。
- 历史 API 为只读；原内容只按该时点 file → blob 关系解析，不允许任意 blob 路径访问。
- 不新增权威状态、不修改 op payload 协议、不让历史回溯触发 metadata 提取或派生媒体任务。

## 实现记录

### 第一阶段：操作历史 API

- 已实现按 box、file、action、group 筛选与 op ID 分页、单条 payload 详情和严格撤销接口；列表不读取 payload，删除后的文件仍可查历史。
- 撤销复用持久请求去重，覆盖重复请求、重复撤销、阻挡操作编号、撤销的撤销和 rebuild 后重试。回执明确不可撤销。
- 修正请求执行层覆盖命令详细错误的问题，保留撤销冲突的 `blocking_op`；已提交或结果不确定的写错误仍优先返回。
- 本地 `go test ./internal/api ./internal/library ./internal/store ./internal/arch` 与 `make check` 通过。后续阶段与远端运行证据继续补充。
