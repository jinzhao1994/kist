## A. 待决问题（阻塞式，有截止里程碑）

### A1. HEIC / ffmpeg 与单二进制的取舍 ⚠️ 最要紧

**截止：M4 之前**（改过三次，见下）

**它和 M3 已经完全无关了**——派生媒体整个移出了 M3，排到 Web UI 之后（设计文档 §7 的 M5），M3 连解码都不碰。

但它**提前**成了 M4 的问题：M4 的网格直接发原图，而 Chrome / Firefox 根本不渲染 HEIC。所以「网格对一个渲染不了的文件显示什么」在 M4 就要有答案，比缩略图管线还早。

底层理由：**HEIC 只挡住缩略图 / 预览这一条路。** 存储、去重、检索、打 tag、撤销、`boxes/` 投影、下载原图全都不需要解码，今天就能工作在 HEIC 文件上。M5 的派生管线因此要按「**降级是默认路径**」规划，而不是「有 ffmpeg 是默认、没有才降级」。

**它也不是「等做 app 再说」的问题**（这是当天先改错了一次的地方）：桌面浏览器上打开的网格照样在显示 iPhone 拍的照片。真正的触发点是有人开始用网格翻自己的库，那比 app 早得多。

`imaging` 和 Go 标准库都不支持 HEIC，而 **iPhone 默认拍出来就是 HEIC**——这不是边角情况，是主流情况。能解码的只有 `libheif`（CGO）或 ffmpeg，视频转码同理。两者都是外部依赖，会破坏单二进制。

倾向方案：**检测到系统 ffmpeg 就启用，检测不到则降级并明确告知用户**（没有 ffmpeg 也能存能搜，只是没有 HEIC 缩略图和视频预览），同时提供一个带 ffmpeg 的完整发行版给不想折腾的用户。

需要确认的：降级时 HEIC 文件在网格里显示什么？通用图标还是占位？用户能不能看出"这是我缺依赖"而不是"这文件坏了"？**降级成为默认路径之后，这一条从「需要确认」升级成「必须做对」**——一个典型 iPhone 用户的网格里会有相当一部分是占位图，说不清楚就是在让人以为自己的照片坏了。

详见设计文档 5.3。

### ~~A3. Web UI 用 React 还是 Vue~~ ✅ 已定（2026-08-28）

**React。** 但**定稿当天补上的那条理由，几小时后就被自己推翻了**，这里如实记一下过程——留一条已知站不住的理由比不写还糟。

- **写下的第三条理由**：手机 app 走 React Native，两端能共享客户端、类型、react-query 的逻辑和业务 hooks
- **推翻它的**：5.4 把 app 的范围收成了「只有备份」。**一个备份引擎和一个浏览用的 web UI 本来就没有东西可共享**，不管两边是不是同一个框架。剩下的只有 API 客户端，而那是 OpenAPI 生成的，Dart 和 TS 一样顺
- **连锁反应**：复用的量既然是零，app 的框架就纯按「iOS 后台上传谁更稳」选，于是 **app 定了 Flutter**（5.4）
- **结论没变**，React 站得住的是原来那两条：贡献者池最大、生态贴得上硬需求。**并且当天顺手否掉了「两边都用 Flutter」**——Flutter Web 画进 canvas，没有 Ctrl-F、没有右键另存为，CanvasKit 的体积过不了 `go:embed` 那一关（这仓库对二进制体积有过判决，见第 8 节的 tzf）

详见设计文档 5.2，那里记着完整的否掉理由和这条教训：**一条「两端能复用」的理由，先量一量能复用的到底是什么。**

## B. 尚未设计的领域（不阻塞 M1，但迟早要谈）

### ~~B1. Query 的排序语义~~ ✅ 已全部定完（2026-08-27）

- ~~**中文排序**~~ ✅ **已定（2026-08-26）**：v0.1 一律 UTF-8 字节序，locale 排序（拼音 / 笔画）作为带触发条件的逃生舱推迟。详见设计文档 4.8——那节记了三个平台的实测、否掉的两条路、以及将来要做时的完整做法。顺带纠正了这里原先的一处错误断言：**码点序不是"基本无意义"，CJK 基本区就是按部首笔画编码的**，它是一种真实的传统字典序，只是不是现代人对文件名排序的期待
- ~~**变精度日期怎么混排**~~ ✅ **已定（2026-08-27）**：不动，前缀字典序就是对的——它翻译过来是「按区间起点排，粗的在前」，一条能讲清楚的规则。让 `2019` 按「年中」排要算排序键，索引就没了。同时定了**筛选取区间重叠而不是包含**（找 2019 年春天时，只知道是「2019 年」的 box 应该出来）。详见设计文档 4.2.1
- ~~**`captured_at` 为空的文件排哪**~~ ✅ **已定（2026-08-27）**：排最后，`ORDER BY captured_at DESC NULLS LAST, id DESC`。详见设计文档 4.5.1——否掉 `COALESCE(captured_at, created_at)` 的不是语义而是索引（实测会退化成 `USE TEMP B-TREE FOR ORDER BY`，keyset 分页的前提没了），而 `id` 是 UUIDv7，`id DESC` 本身就等于 `created_at DESC`，回退语义由 tie-breaker 免费办掉。顺带挖出一条引擎分歧记进了 4.7：**Postgres 的 `DESC` 默认 `NULLS FIRST`，必须显式写 `NULLS LAST`**
- ~~**keyset 游标要编码完整的排序元组**~~ ✅ **已定（2026-08-27）**：`cursor = base64(sortID ␀ sortKey ␀ id)`，请求的排序和游标里的对不上就**报错**，不是尽力而为。详见设计文档 4.2.1

### B1b. M1c 期间暴露出来、仍然没定的

**M4 之前**

- **投影脏标记在 UI 里长什么样。** CLI 里是打开库时往 stderr 提示一行、`kist relink` 之后说一句「warning is cleared」。3.4.1 只要求「在 UI 上可见」，Web UI 那边该是什么形态没想过——横幅？box 上的角标？点一下就能修？
- **导入没有断点续传。** M1c 的中断语义是「停下并提交已完成的」，重跑靠的是幂等——但幂等意味着**已导入的文件会被重新读一遍、重新哈希一遍**才发现该跳过。几百个文件无所谓，500 GB 上这不便宜。真正的续传要和 B2 的任务模型一起解决
- **跨 box / 跨 folder 移动文件还没有 op。** M1c 只有导入和删除。`write()` 里「folder 链在 Apply 前后各采样一次」的设计已经为它留好了位置（前一次给旧链，后一次给新链），但 op 本身、它的严格撤销语义、以及投影侧怎么响应都还没设计
- **每次写都要重算一遍全部 box 的目录名。** 投影的增量维护要靠它判断有没有发生撞名连锁（3.4.1）。box 数量级是几百到几千，一次 `SELECT` 加一次排序，现在完全不是问题；但它是随 box 数线性的，将来 `serve` 下每个请求都写一次时要重新看

### ~~B1c. M2b（Query 契约）开写前必须定的四件事~~ ✅ 已定（2026-08-27）

四条全部写进了设计文档 **4.2.1**，连同否掉的路：

| | 结论 |
|---|---|
| `Kinds []MediaKind` | **砍掉**，M3 跟提取管线一起落地。存一列会让改扩展名映射表变成 `verify --deep` 报 `ViewDrift`；查询时现算则是在撒谎——扩展名不是 kind |
| `Tags TagExpr` | **真做成 AND/OR/NOT 树**。没有 UI 反而正是 conformance suite 存在的理由，它是这条路径唯一的行使者 |
| `Sort SortSpec` | 做 `captured` / `imported` / `name`，**`size` 砍掉**（唯一要 join 且没有索引能支撑，必然退化成临时 B-tree）。游标带排序标识，对不上就报错 |
| `Time *DateRange` | **区间重叠**，排序保持前缀字节序。`captured_at` 为 NULL 的文件不进时间筛选，所以 M3 之前文件的时间筛选返回空——这是事实，不是缺陷 |

### B1d. M2a 期间暴露出来、仍然没定的

**M4 之前**

- **远端只有「有没有」，没有「新不新」。** 修复只按哈希取，所以永远不会拿到错内容——但也永远不知道远端是不是过期的。用户配了一个三年前 rsync 过的远端，`kist repair` 会安安静静地什么都修不了，而输出看起来像「这块盘没这个文件」。要不要记一下远端最后一次被验证的时间、要不要在 `remote list` 里提示「这个远端比你的库少 4000 个 blob」，都没想过
- **`repair` 没有进度。** 从一块 USB 2.0 的移动硬盘修 200 GB 是几个小时，而现在它一声不吭。`scrub` 有进度回调，`repair` 该抄一份，但它的进度单位是字节不是文件数（一个 4 GB 的视频和一张 2 MB 的照片不是一回事），得重想
- ~~**`scrub` 把「多进程」从理论变成了日常。**~~ ✅ **B3 已定（2026-08-27）**：`scrub` / `verify` / `repair` **不持写锁**，边 scrub 边导入是被支持的——禁止它等于没人会跑 scrub。安全性的两条理由（前两者不写；`repair` 只写内容寻址的 blob，且结构上写不出 op）见设计文档 2.7
- **`verify --deep` 的开销要在大一个数量级的库上重测。** 3.8 记了 4000 文件 / 502 op 上的实测（0.38 s），但十一条 `EXCEPT` 是随行数增长的，4000 个文件证明不了 40 万个

### B1e. M2b 期间暴露出来、仍然没定的

**M4 之前**

- **`find` 每一行都单独解析一次路径和 box。** `library.FileLocation` 对每个结果行走一遍 folder 链（2026-09-04 之前是读整个 box 的 folder 表，更贵），一千行就是一千次。4000 文件的库上完全量不出来（整个查询淹没在进程启动里），但它是随结果行数线性的数据库往返，`serve` 下每个请求都这么干时要重新看。真做的话是一次性把涉及的 folder 链批量取回来

- **`files` 按 box 筛的实际代价没量过。** 2026-09-04 去掉 `files.box_id` / `folders.box_id` 之后，`find --box` 变成一次从 `boxes.root_folder_id` 出发的递归下降。设计文档 1.5 记了为什么这个取舍值得，但**没有数字**——而 4000 文件的测试库上量不出来（同 1748 对 `scrub` 说的那件事），要造十万行的合成库才有意义。若真慢，加回来是一次 `rebuild` 不是数据迁移
- **`Query` 只回答文件，不回答 box。** 4.2 的 `Time` 那句「box 时间范围 或 文件拍摄时间」到 M2b 只落地了文件那一半；box 列表走的还是 `ListBoxes` 那套独立的选项结构。conformance suite 因此也只覆盖文件。box 查询要不要统一进同一个契约（还是它本来就该是另一个契约）没想过
- **契约没有说结果总数。** 网格 UI 想显示「共 1234 项」，而 keyset 分页天生不知道总数。要么加一个单独的 count 查询（4.4 认下的全扫上它和查询一样贵），要么 UI 不显示总数。M4 之前要选一个

### B1f. M3（提取与派生）开写前还剩的五件事

**四件存储侧的已定**（2026-08-27/28，详见设计文档 1.7）：metadata 的权威是 op log 不是 `blobs/`；payload 只带真的变了的键；展开规则按形状不按有用性；只挂在 file 上、带真外键。

**剩下五件没定：**

1. **`captured_at` 放哪。** 留在 `files` 上（keyset 索引不用动）还是挪进派生表（join 一次，索引跟着走）。它现在是 `files` 的列，而它的值来自提取
2. **ffmpeg 怎么探测**（A1 的落地）。启动时探一次并像 link mode 那样写进 `kist.toml`，还是每次用时探？link mode 已经有先例（3.5），但它探的是文件系统，ffmpeg 是可执行文件，会被用户中途装上
3. **派生状态要不要显式记录。**「没有缩略图」今天分不出是「还没生成」「生成失败」还是「缺 ffmpeg 生成不了」。而**装上 ffmpeg 之后必须能自动补做**——那要求有状态，不只是「文件在不在」
4. **缩略图到底同步不同步。** 3.6 说导入时同步生成，但 M3 结束时没有任何界面看得见它，而解码 + 缩放会让导入明显变慢。M3 是不是应该纯懒生成
5. **视频转码队列 vs B2。** B2（任务模型）是 M4 的前置。M3 自己搭一个小的持久队列让 B2 去泛化，还是视频整个推到 M4？风险是把任务模型写两遍

### B2. 长时间操作的任务模型

**~~M4 之前必须有~~ → 手机端自动同步之前必须有**（改于 2026-08-28）

推迟的理由见设计文档 §7 M4 的「为什么 M4 不需要任务模型」，三条：**2.8 把运维命令划归 CLI**，所以真会跑几小时的东西不上 web；**上传进度是浏览器原生的**；**提取进度是一次 `COUNT` 而不是任务状态**。最难的那一处（任务与 op 的关系）其实已经被 3.7.1 解决了——它绑的是 `ctx.Done()`，而一个被掐断的 HTTP 请求和 Ctrl-C 是同一个信号。

**失效条件：有一个客户端挂在那里等。** 5.4 的手机 app 后台同步不满足，那时下面三条会原样回来。

> **同一天稍后，A4 把这条从「可能」变成了「一定」**：作者确认一定会做自动备份 app。所以 B2 不再是一个「也许永远用不上」的子系统，**它一定会被需要，只是不在 v0.1**。推迟的理由一条没变（M4 确实不需要它），但别再把它当成可以无限期搁置的东西。
>
> B7 里那条「备份状态是不是要进 op log」和这里是同一个问题的两半，会一起解决。

导入 500 GB、`scrub` 全库、视频转码——都不可能是一个同步的 HTTP 请求。需要：

- 任务提交 / 进度查询（轮询还是 SSE）/ 取消
- 中断后能否续传（导入到一半关了浏览器）
- 任务与 op 的关系：一次导入是**一条** op（批粒度已经定了），但任务可能跑几小时——op 是在任务结束时才写入吗？那中途崩了就全丢了。还是拆成多条 op？这与"批量操作 = 一条 op = 一次撤销"的既定语义有张力，**需要专门想清楚**
- ~~CLI 那边同样的问题：`kist import` 跑到一半 Ctrl-C 怎么办~~ ✅ **已定（2026-08-27）**：优雅停止，已完成的部分提交成**一条** op；第二次 Ctrl-C 才强制退出。配套定了导入幂等（同 folder 同 name 同 `blob_key` 就跳过），所以中断后重跑同一个目录是收敛的。详见设计文档 3.7.1。**这只解决了 CLI 单进程的同步导入**——serve 侧的异步任务模型（进度、取消、续传、任务与 op 的关系）仍然全部未定

这是个不小的子系统，别低估。

### ~~B3. 并发与多进程~~ ✅ 已定（2026-08-27）

**结论：`kist.lock` 上一把作用域为「一次逻辑写操作」的 OS 咨询锁，加上一条规则——进程内不放任何「别的进程能让它作废」的状态。详见设计文档 2.7。**

> 后半句在 2026-08-28 改过一次。原来写的是「读路径比一次 `MAX(ops.id)`，不同就重载缓存」。推翻的理由：版本号方案要求每一处进程内状态都记得挂上检查，**漏一处是个静默 bug 而且没有任何测试会发现**——测试跑在一个进程里，那正是缓存永远正确的那种情况。而 kist 部署在用户自己的设备上，没有吞吐量在替缓存说话。两处状态因此都拿掉了：投影目录名的「之前」改在写内取（它根本不是缓存），tag 树改成按需的定点查询（名字解析走唯一索引，子树展开走递归 CTE）。版本号没被否掉，它降级成一个可选的新鲜度特性，不再是 M4 的前置条件。

读代码定的，过程中有四条事实推翻了本条原来的前提：

1. **SQLite 争用不是问题。** 导入的哈希和落盘全在事务外，只有最后写 op 那一下进事务（毫秒级），WAL 下读者又不阻塞。「库级锁用户体验差」这条指控因此站不住
2. **最严重的失效不是 tag 树，是投影目录名缓存。** 它过期会让 `boxes/` 静默多出一个目录，两份链接指向同一批文件。这个缓存原来在设计文档里根本没写，已补进 3.4.1
3. ~~**版本号早就存在。** 3.12 定了「op ID 就是版本号」，所以缓存失效判断不需要发明新概念~~ —— 这条事实没错，但它导向的结论（用版本号作废缓存）已推翻，见上面的注
4. **有一个事务外的读-改-写窗口**（导入的文件名分配 vs `files(folder_id, name)` 的 UNIQUE 索引），它的作用域比数据库事务宽，SQLite 自己的锁救不了——这是唯一真正需要一把锁的地方

**原倾向「CLI 检测到 serve 就走 HTTP API」被推翻**，理由写在 2.7 的否掉清单里：它为了修一个缓存问题给整个 CLI 上税，把 CLI 的发布节奏绑死在 API 完整度上，而「serve 在不在跑」这个检测本身比原问题还难做对。

**还没解决的两条：**

- **② 已经解决**（2026-08-28）：见上面的注。原来这里挂着「读路径比 `MAX(ops.id)`——只有 serve 需要，等 serve」
- **tag 成环窗口已关闭（2026-10-01）**：提交时持锁并追赶日志后重查祖先链，覆盖普通移动和撤销；命令层检查不再是唯一保证。详见 2.7。
- **③ 导入的名字分配没被这把锁修好。** 它的窗口是整个导入（几小时），持锁到底会让 serve 上建个 tag 卡三小时。选了「不持锁，撞了就整批失败」——它响、它收敛、触发条件很窄。真正的修法是**提交前在锁里重新解析一遍名字和新建 folder**，要改导入 payload 的构造，值得单独一轮。详见设计文档 2.7 的实现记录
- **检查一致性已修正（2026-10-01）**：`verify` 持库写锁，保证日志与视图比较不会夹入提交；`scrub` / `repair` 仍无锁，结果是检查期间逐文件观察，不是某一瞬间的全库快照。后台报告的过期展示仍留给 B2。

### B4. `kist init` 的交互流程 —— 大部分已定

**M1**

路径选择、探测结果展示、非交互模式已定，见设计文档 3.1。剩下没定的只有一条：**要不要提供可选的初始 tag 树模板**（`人物 / 地点 / 证件 / 财务` 一类）。空树对新用户不友好，预设树又容易和每个人的习惯打架。倾向不做，但如果做，它是纯数据、随时可删。

### B5. 前端的信息架构

**M4**

完全没谈过 UI 长什么样。box 列表和网格视图的关系、tag 树选择器怎么摆、筛选面板的交互、时间轴视图要不要做、证件这类"当前有效状态"的东西在没有 metadata 的 v0.1 里怎么呈现。

### ~~B6. 错误模型~~ ✅ 已定（2026-08-28）

**结论：码是契约、句子是 fallback；七个类，HTTP 状态和退出码从类推导；`errcodes.Of()` 是纯函数不是注册表；结构化字段是命名字段不是自由袋子。详见设计文档 2.9。**

三条原来挂着的都定了：

- **字符串码 vs 仅 HTTP 状态** → 两个都要，但**码是权威、状态是投影**。HTTP 区分不了「tag 重名」和「box 重名」，都是 409，而客户端要对它们做不同的事
- **严格撤销冲突要能说出是哪条 op 挡住的** → `undo_blocked` 带 `blocking_op` 字段。人话那半在 2.5 实现时就有了（`explainBlockedUndo`），缺的一直是**数据**——UI 想把「51」渲染成一个能点的按钮，不想去 parse 英文
- **其余批量操作怎么表达全有全无** → 定成一条规则：**只有输入来自库外部的操作允许部分成功**。`import` 读磁盘，读不了一个是正常的星期二；`tag_files` 的输入是你自己库里的 id，坏一个是 bug，静默跳过会把真问题藏起来

定的过程里发现了一件原来的方案办不到的事：**「每个包用 `init()` 注册自己的码」结构上不成立**，`domain` 和 `query` 不许 import 任何东西，而两个 sentinel 就住在那里。改成纯函数，顺带避开了 `exif` 那次 `init()` 从没跑过的坑。

### B7. 手机 app 的范围与它和 PWA 的边界

**手机 app 开工前**

5.4 把「app 只做备份、浏览交给 PWA」定成了硬约束，但那条线具体划在哪没定：

- **备份的 app 里到底要不要能看东西。** 「刚备份完的这批照片传上去了吗」是个合理需求，而它已经是一个列表界面了。一个只有进度条的 app 和一个有薄相册的 app 差着一整块工作量
- **PWA 到底够不够。** 5.4 说「PWA 几乎零成本」，那是关于**技术可行性**的判断，不是关于**手感**的。在手机上滑一个上万张图的虚拟滚动网格，PWA 和原生差多少，没有实测过——而这个差距如果太大，「浏览交给 PWA」这条约束就会自己松掉
- **备份状态是不是要进 op log。** 「这台手机上的哪些照片已经备份过了」是客户端状态还是库的状态？记进库里就要有 op 和表；只在客户端记，换手机就全丢、要重扫一遍相册。这条**会影响 schema**，比另外两条更早需要答案
- **⏸ 备选路径的触发条件**：原生薄壳 + WebView 装 PWA + 原生备份模块（5.4 已记录）

### B8. `file_metadata` 的值类型：1.7.5 否掉 manifest typing 的理由已经作废

**触发条件：v0.2 的 metadata 搜索需要数值比较**（与设计文档第 8 节那一行同一条）

4.1 取消了 Postgres 实现，而 1.7.5 否掉 SQLite manifest typing 的**唯一**理由是「可移植性不是能力」——那句话现在没有指涉对象了。被放弃的是一个实测有效的能力：不带 affinity 的列里整数、实数、文本各按自己的方式排，索引照样走 `SEARCH … USING COVERING INDEX`，负数时间戳排在正确的位置。

两个候选：

| | 代价 |
|---|---|
| **`value_int` / `value_real` 旁列**（原定方案） | 两列常年为 NULL；写入侧要按 `type` 分流；查询要按类型选列 |
| **manifest typing**（重开的方案） | Go 侧 `Scan` 要处理动态类型；`type` 列与实际存储类型可能不一致，需要一处守卫；**改列 affinity 要重建表**，而 `file_metadata` 从 M3 起每次导入都有行 |

**别顺手就翻案。** 这一条被引进 4.1 当作「双实现那笔税」的实物证据，但「税收错了」不等于「反向的选择自动正确」——manifest typing 有它自己要付的账，上表右列那三条都还没实测过。决定要在真做 metadata 搜索时连同索引形状一起做，不该单独提前。

### B9. B 在 A 的库上留下的 metadata 存在哪

**触发条件：分享功能开写前**（第 8 节里「分享 / 邀请链接 / grantee 账号」那一行）

4.1 把交付形态定成「一人一实例，官方服务不托管数据」，同时记下了它要支持的场景：A 把照片分享给 B，**B 能在 A 的数据上留一些 metadata（比如收藏）**。这个场景动两处已定的设计，而且方向还没定：

- **存在 A 的库里。** 那么 A 的 op log 里会出现不是 A 写的 op，需要一套远程写入的授权模型；而且 `ops.origin` 只有「哪一类执行者」，回答不了「哪一个人」——**这会让 `ops.actor` 的删除理由失效**。那一列删掉的理由是「每行都是 `"cli"`，而 `"cli"` 回答的是 `origin` 的问题不是 actor 的问题」，当时完全正确，但这个场景会带来第一个真正的 actor
- **存在 B 自己的库里。** A 的 op log 保持只有 A 写，分享是纯只读的，不需要授权模型——更符合「一人一实例」。代价是 B 的库里要能引用一个不属于它的文件

**还有一层更基本的问题：「收藏」到底是文件的属性，还是观察者的属性？** A 的收藏和 B 的收藏是两回事，而 1.7 定的是 `(file_id, key)` 单一所有者（命名空间互斥）。硬塞进同一个槽位要么互相覆盖，要么就得往主键里加一个 owner 维度——**而那正是「把 source 加进 `file_tags` 主键」被否掉的形状**（三处计数会静默翻倍）。倾向于「观察者的属性」，那样它根本不该住在被观察那一侧。
