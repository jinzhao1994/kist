## A. 待决问题（阻塞式，有截止里程碑）

### A1. HEIC / ffmpeg 与单二进制的取舍 ⚠️ 最要紧

**截止：M3 开始前**

`imaging` 和 Go 标准库都不支持 HEIC，而 **iPhone 默认拍出来就是 HEIC**——这不是边角情况，是主流情况。能解码的只有 `libheif`（CGO）或 ffmpeg，视频转码同理。两者都是外部依赖，会破坏单二进制。

倾向方案：**检测到系统 ffmpeg 就启用，检测不到则降级并明确告知用户**（没有 ffmpeg 也能存能搜，只是没有 HEIC 缩略图和视频预览），同时提供一个带 ffmpeg 的完整发行版给不想折腾的用户。

需要确认的：降级时 HEIC 文件在网格里显示什么？通用图标还是占位？用户能不能看出"这是我缺依赖"而不是"这文件坏了"？

详见设计文档 5.3。

### ~~A2. 库目录的默认位置~~ ✅ 已定（2026-08-22）

交互式流程（`ssh-keygen` 形态），默认 `~/kist`，创建前摊开探测结果。详见设计文档 3.1。

### A3. Web UI 用 React 还是 Vue

**截止：M4 开始前**

选 React 的核心理由是贡献者池最大。但如果实际预期贡献者主要来自国内，Vue 的份额优势是真实的。届时换掉成本仍然可控（M4 才开始写前端）。

## B. 尚未设计的领域（不阻塞 M1，但迟早要谈）

### B1. Query 的排序语义 —— 中文排序已定，其余待定

**剩下两条到 M2b 变成阻塞项，见 B1c**

- ~~**中文排序**~~ ✅ **已定（2026-08-26）**：v0.1 一律 UTF-8 字节序，locale 排序（拼音 / 笔画）作为带触发条件的逃生舱推迟。详见设计文档 4.8——那节记了三个平台的实测、否掉的两条路、以及将来要做时的完整做法。顺带纠正了这里原先的一处错误断言：**码点序不是"基本无意义"，CJK 基本区就是按部首笔画编码的**，它是一种真实的传统字典序，只是不是现代人对文件名排序的期待
- **变精度日期怎么混排。** 升序时 `2019`（只知年份）排在 `2019-01` 之前——因为 ISO-8601 前缀的字典序如此。但用户期待的是这样吗？还是应该按"年中"来排？两种都说得通，要选一个并写进 spec
- ~~**`captured_at` 为空的文件排哪**~~ ✅ **已定（2026-08-27）**：排最后，`ORDER BY captured_at DESC NULLS LAST, id DESC`。详见设计文档 4.5.1——否掉 `COALESCE(captured_at, created_at)` 的不是语义而是索引（实测会退化成 `USE TEMP B-TREE FOR ORDER BY`，keyset 分页的前提没了），而 `id` 是 UUIDv7，`id DESC` 本身就等于 `created_at DESC`，回退语义由 tie-breaker 免费办掉。顺带挖出一条引擎分歧记进了 4.7：**Postgres 的 `DESC` 默认 `NULLS FIRST`，必须显式写 `NULLS LAST`**
- **keyset 游标要编码完整的排序元组。** 排序键换了，旧游标必须失效而不是给出错乱结果。4.8 的逃生舱里已经把"改 locale 要让游标失效"写进去了，但通用机制还没设计

### B1b. M1c 期间暴露出来、仍然没定的

**M4 之前**

- **投影脏标记在 UI 里长什么样。** CLI 里是打开库时往 stderr 提示一行、`kist relink` 之后说一句「warning is cleared」。3.4.1 只要求「在 UI 上可见」，Web UI 那边该是什么形态没想过——横幅？box 上的角标？点一下就能修？
- **导入没有断点续传。** M1c 的中断语义是「停下并提交已完成的」，重跑靠的是幂等——但幂等意味着**已导入的文件会被重新读一遍、重新哈希一遍**才发现该跳过。几百个文件无所谓，500 GB 上这不便宜。真正的续传要和 B2 的任务模型一起解决
- **跨 box / 跨 folder 移动文件还没有 op。** M1c 只有导入和删除。`write()` 里「folder 链在 Apply 前后各采样一次」的设计已经为它留好了位置（前一次给旧链，后一次给新链），但 op 本身、它的严格撤销语义、以及投影侧怎么响应都还没设计
- **每次写都要重算一遍全部 box 的目录名。** 投影的增量维护要靠它判断有没有发生撞名连锁（3.4.1）。box 数量级是几百到几千，一次 `SELECT` 加一次排序，现在完全不是问题；但它是随 box 数线性的，将来 `serve` 下每个请求都写一次时要重新看

### B1c. M2b（Query 契约）开写前必须定的四件事

**截止：M2b 开始前**（设计文档第 7 节列了同一张表，那里是里程碑视角，这里是待决问题视角）

4.2 的 `Query` 是 DAL 的契约，conformance suite 围着它写。但它有四个字段现在落不了地：

- **`Kinds []MediaKind` 没有数据。** schema 里没有 kind 列，代码里没有这个概念，1.7 说 v0.1 的 metadata 只有 `file:size` / `file:mtime`，提取管线在 M3。三条路：从扩展名现算（便宜，但改了映射表旧结果就变）、加一列在导入时算（要 schema 改动 + 一次 rebuild）、**从 `Query` 里砍掉留到 M3**（倾向，但那样 conformance suite 就不是「围着 4.2 写完的」）
- **`Tags TagExpr` 要不要真做成 AND/OR/NOT 树。** 现在是扁平的 `AllOf` / `NoneOf`，CLI 也没有布尔语法。4.3 定的语义（选中一个 tag 默认含后代）在两种形态下都成立，所以这是「契约要多宽」的问题，不是语义问题
- **`Sort SortSpec` 的四个键怎么和 keyset 共存。** 4.5 的游标现在写死 `captured_at, id`；按大小排要 join `blobs`；按文件名排在 4.8 定的字节序下是确定的，但游标要带上完整排序元组——这一条 B1 里已经记了，到 M2b 变成阻塞项
- **`Time *DateRange` 与变精度日期怎么混排。** B1 里那条「升序时 `2019` 排在 `2019-01` 之前，用户期待的是这样吗」到这里必须选一个

### B1d. M2a 期间暴露出来、仍然没定的

**M4 之前**

- **远端只有「有没有」，没有「新不新」。** 修复只按哈希取，所以永远不会拿到错内容——但也永远不知道远端是不是过期的。用户配了一个三年前 rsync 过的远端，`kist repair` 会安安静静地什么都修不了，而输出看起来像「这块盘没这个文件」。要不要记一下远端最后一次被验证的时间、要不要在 `remote list` 里提示「这个远端比你的库少 4000 个 blob」，都没想过
- **`repair` 没有进度。** 从一块 USB 2.0 的移动硬盘修 200 GB 是几个小时，而现在它一声不吭。`scrub` 有进度回调，`repair` 该抄一份，但它的进度单位是字节不是文件数（一个 4 GB 的视频和一张 2 MB 的照片不是一回事），得重想
- **`scrub` 把「多进程」从理论变成了日常。** B3 说并发问题 M4 之前必须定，前提是「M1 只有 CLI 时不会暴露」。scrub 是第一个真的会跑几小时的命令，而人在它跑着的时候当然会想继续导入
- **`verify --deep` 的开销要在大一个数量级的库上重测。** 3.8 记了 4000 文件 / 502 op 上的实测（0.38 s），但十一条 `EXCEPT` 是随行数增长的，4000 个文件证明不了 40 万个

### B2. 长时间操作的任务模型

**M4 之前必须有**

导入 500 GB、`scrub` 全库、视频转码——都不可能是一个同步的 HTTP 请求。需要：

- 任务提交 / 进度查询（轮询还是 SSE）/ 取消
- 中断后能否续传（导入到一半关了浏览器）
- 任务与 op 的关系：一次导入是**一条** op（批粒度已经定了），但任务可能跑几小时——op 是在任务结束时才写入吗？那中途崩了就全丢了。还是拆成多条 op？这与"批量操作 = 一条 op = 一次撤销"的既定语义有张力，**需要专门想清楚**
- ~~CLI 那边同样的问题：`kist import` 跑到一半 Ctrl-C 怎么办~~ ✅ **已定（2026-08-27）**：优雅停止，已完成的部分提交成**一条** op；第二次 Ctrl-C 才强制退出。配套定了导入幂等（同 folder 同 name 同 `blob_key` 就跳过），所以中断后重跑同一个目录是收敛的。详见设计文档 3.7.1。**这只解决了 CLI 单进程的同步导入**——serve 侧的异步任务模型（进度、取消、续传、任务与 op 的关系）仍然全部未定

这是个不小的子系统，别低估。

### B3. 并发与多进程

**M4 之前必须定**（M1 只有 CLI 时不会暴露）

设计文档 1.6 写了一条前提假设：**内存 tag 树的一致性依赖「`library` 是唯一写入口 + 单进程」**。但 `kist serve` 和 `kist import` 是两个进程，一旦同时跑，这个假设就破了——SQLite 的文件锁能保证数据不坏，但 serve 进程里的内存 tag 树和计数会静默过期。

三个选项：

| | 说明 |
|---|---|
| **CLI 检测到 serve 在跑就走 HTTP API**（倾向） | CLI 退化成客户端，单写者假设自然成立。代价：CLI 依赖 serve 的 API 完整度 |
| 库级排他锁 | 同一时刻只有一个进程能写，另一个直接报错退出。最简单，但用户体验差 |
| 放弃内存树 | 每次查 DB。丢掉 1.6 那套简化 |

### B4. `kist init` 的交互流程 —— 大部分已定

**M1**

路径选择、探测结果展示、非交互模式已定，见设计文档 3.1。剩下没定的只有一条：**要不要提供可选的初始 tag 树模板**（`人物 / 地点 / 证件 / 财务` 一类）。空树对新用户不友好，预设树又容易和每个人的习惯打架。倾向不做，但如果做，它是纯数据、随时可删。

### B5. 前端的信息架构

**M4**

完全没谈过 UI 长什么样。box 列表和网格视图的关系、tag 树选择器怎么摆、筛选面板的交互、时间轴视图要不要做、证件这类"当前有效状态"的东西在没有 metadata 的 v0.1 里怎么呈现。

### B6. 错误模型

**M4 之前**

- 稳定的错误码体系（字符串码 vs 仅 HTTP 状态）
- **严格撤销冲突要能表达"是哪条 op 挡住了"**（见设计文档 2.5），否则用户只看到"撤销失败"没法处理
- ~~批量操作的部分失败~~ ✅ **导入这一侧已定（2026-08-27）**：per-file 结果（导入 / 跳过 / 失败 + 原因），失败的文件根本不进 payload，所以 op 本身依然原子。写进了设计文档 3.7.1。**其余批量操作仍是全有全无**，错误码体系怎么表达这个差异还没定
