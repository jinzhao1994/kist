## A. 待决问题（阻塞式，有截止里程碑）

### A1. HEIC / ffmpeg 与单二进制的取舍 ⚠️ 最要紧

**截止：网格浏览成为主要界面时**（2026-08-27 从「M3 开始前」改）

改的理由：**HEIC 只挡住缩略图 / 预览这一条路。** 存储、去重、检索、打 tag、撤销、`boxes/` 投影、下载原图全都不需要解码，今天就能工作在 HEIC 文件上。所以 M3 可以照常开写，只是要按「**降级是默认路径**」规划，而不是「有 ffmpeg 是默认、没有才降级」。

**但它不是「等做 app 再说」的问题**：桌面浏览器上打开的网格照样在显示 iPhone 拍的照片。真正的触发点是有人开始用网格翻自己的库，那比 app 早得多。

`imaging` 和 Go 标准库都不支持 HEIC，而 **iPhone 默认拍出来就是 HEIC**——这不是边角情况，是主流情况。能解码的只有 `libheif`（CGO）或 ffmpeg，视频转码同理。两者都是外部依赖，会破坏单二进制。

倾向方案：**检测到系统 ffmpeg 就启用，检测不到则降级并明确告知用户**（没有 ffmpeg 也能存能搜，只是没有 HEIC 缩略图和视频预览），同时提供一个带 ffmpeg 的完整发行版给不想折腾的用户。

需要确认的：降级时 HEIC 文件在网格里显示什么？通用图标还是占位？用户能不能看出"这是我缺依赖"而不是"这文件坏了"？**降级成为默认路径之后，这一条从「需要确认」升级成「必须做对」**——一个典型 iPhone 用户的网格里会有相当一部分是占位图，说不清楚就是在让人以为自己的照片坏了。

详见设计文档 5.3。

## B. 尚未设计的领域（不阻塞 M1，但迟早要谈）

### ~~B1. Query 的排序语义~~ ✅ 已全部定完（2026-08-27）

- ~~**中文排序**~~ ✅ **已定（2026-08-26）**：v0.1 一律 UTF-8 字节序，locale 排序（拼音 / 笔画）作为带触发条件的逃生舱推迟。详见设计文档 4.8——那节记了三个平台的实测、否掉的两条路、以及将来要做时的完整做法。顺带纠正了这里原先的一处错误断言：**码点序不是"基本无意义"，CJK 基本区就是按部首笔画编码的**，它是一种真实的传统字典序，只是不是现代人对文件名排序的期待
- ~~**变精度日期怎么混排**~~ ✅ **已定（2026-08-27）**：不动，前缀字典序就是对的——它翻译过来是「按区间起点排，粗的在前」，一条能讲清楚的规则。让 `2019` 按「年中」排要算排序键，索引就没了。同时定了**筛选取区间重叠而不是包含**（找 2019 年春天时，只知道是「2019 年」的 box 应该出来）。详见设计文档 4.2.1
- ~~**`captured_at` 为空的文件排哪**~~ ✅ **已定（2026-08-27）**：排最后，`ORDER BY captured_at DESC NULLS LAST, id DESC`。详见设计文档 4.5.1——否掉 `COALESCE(captured_at, created_at)` 的不是语义而是索引（实测会退化成 `USE TEMP B-TREE FOR ORDER BY`，keyset 分页的前提没了），而 `id` 是 UUIDv7，`id DESC` 本身就等于 `created_at DESC`，回退语义由 tie-breaker 免费办掉。顺带挖出一条引擎分歧记进了 4.7：**Postgres 的 `DESC` 默认 `NULLS FIRST`，必须显式写 `NULLS LAST`**
- ~~**keyset 游标要编码完整的排序元组**~~ ✅ **已定（2026-08-27）**：`cursor = base64(sortID ␀ sortKey ␀ id)`，请求的排序和游标里的对不上就**报错**，不是尽力而为。详见设计文档 4.2.1

### B1b. M1c 期间暴露出来、仍然没定的

**M4 之前**

- **投影脏标记在 UI 里长什么样。** CLI 里是打开库时往 stderr 提示一行、`kist relink` 之后说一句「warning is cleared」。3.4.1 只要求「在 UI 上可见」，Web UI 那边该是什么形态没想过——横幅？box 上的角标？点一下就能修？
- **导入没有断点续传。** M1c 的中断语义是「停下并提交已完成的」，重跑靠的是幂等——但幂等意味着**已导入的文件会被重新读一遍、重新哈希一遍**才发现该跳过。几百个文件无所谓，500 GB 上这不便宜。真正的续传要和 B2 的任务模型一起解决
- **跨 box / 跨 folder 移动文件还没有 op。** M1c 只有导入和删除。`write()` 里「folder 链在 Apply 前后各采样一次」的设计已经为它留好了位置（前一次给旧链，后一次给新链），但 op 本身、它的严格撤销语义、以及投影侧怎么响应都还没设计
- **每次写都要重算一遍全部 box 的目录名。** 投影的增量维护要靠它判断有没有发生撞名连锁（3.4.1）。box 数量级是几百到几千，一次 `SELECT` 加一次排序，现在完全不是问题；但它是随 box 数线性的，将来 `serve` 下每个请求都写一次时要重新看

### ~~B1c. M2b（Query 契约）开写前必须定的四件事~~ ✅ 已定（2026-08-27）

四条全部写进了设计文档 **4.2.1**，连同否掉的路：

| | 结论 |
|---|---|
| `Kinds []MediaKind` | **砍掉**，M3 跟提取管线一起落地。存一列会让改扩展名映射表变成 `verify --deep` 报 `ViewDrift`；查询时现算则是在撒谎——扩展名不是 kind |
| `Tags TagExpr` | **真做成 AND/OR/NOT 树**。没有 UI 反而正是 conformance suite 存在的理由，它是这条路径唯一的行使者 |
| `Sort SortSpec` | 做 `captured` / `imported` / `name`，**`size` 砍掉**（唯一要 join 且没有索引能支撑，必然退化成临时 B-tree）。游标带排序标识，对不上就报错 |
| `Time *DateRange` | **区间重叠**，排序保持前缀字节序。`captured_at` 为 NULL 的文件不进时间筛选，所以 M3 之前文件的时间筛选返回空——这是事实，不是缺陷 |

### B1d. M2a 期间暴露出来、仍然没定的

**M4 之前**

- **远端只有「有没有」，没有「新不新」。** 修复只按哈希取，所以永远不会拿到错内容——但也永远不知道远端是不是过期的。用户配了一个三年前 rsync 过的远端，`kist repair` 会安安静静地什么都修不了，而输出看起来像「这块盘没这个文件」。要不要记一下远端最后一次被验证的时间、要不要在 `remote list` 里提示「这个远端比你的库少 4000 个 blob」，都没想过
- **`repair` 没有进度。** 从一块 USB 2.0 的移动硬盘修 200 GB 是几个小时，而现在它一声不吭。`scrub` 有进度回调，`repair` 该抄一份，但它的进度单位是字节不是文件数（一个 4 GB 的视频和一张 2 MB 的照片不是一回事），得重想
- ~~**`scrub` 把「多进程」从理论变成了日常。**~~ ✅ **B3 已定（2026-08-27）**：`scrub` / `verify` / `repair` **不持写锁**，边 scrub 边导入是被支持的——禁止它等于没人会跑 scrub。安全性的两条理由（前两者不写；`repair` 只写内容寻址的 blob，且结构上写不出 op）见设计文档 2.7
- **`verify --deep` 的开销要在大一个数量级的库上重测。** 3.8 记了 4000 文件 / 502 op 上的实测（0.38 s），但十一条 `EXCEPT` 是随行数增长的，4000 个文件证明不了 40 万个

### B1e. M2b 期间暴露出来、仍然没定的

**M4 之前**

- **`find` 每一行都单独解析一次路径。** `FilePath` 对每个结果行走一遍 folder 链，一千行就是一千次。4000 文件的库上完全量不出来（整个查询淹没在进程启动里），但它是随结果行数线性的数据库往返，`serve` 下每个请求都这么干时要重新看。真做的话是一次性把涉及的 folder 链批量取回来
- **`Query` 只回答文件，不回答 box。** 4.2 的 `Time` 那句「box 时间范围 或 文件拍摄时间」到 M2b 只落地了文件那一半；box 列表走的还是 `ListBoxes` 那套独立的选项结构。conformance suite 因此也只覆盖文件。box 查询要不要统一进同一个契约（还是它本来就该是另一个契约）没想过
- **契约没有说结果总数。** 网格 UI 想显示「共 1234 项」，而 keyset 分页天生不知道总数。要么加一个单独的 count 查询（4.4 认下的全扫上它和查询一样贵），要么 UI 不显示总数。M4 之前要选一个

### B2. 长时间操作的任务模型

**M4 之前必须有**

导入 500 GB、`scrub` 全库、视频转码——都不可能是一个同步的 HTTP 请求。需要：

- 任务提交 / 进度查询（轮询还是 SSE）/ 取消
- 中断后能否续传（导入到一半关了浏览器）
- 任务与 op 的关系：一次导入是**一条** op（批粒度已经定了），但任务可能跑几小时——op 是在任务结束时才写入吗？那中途崩了就全丢了。还是拆成多条 op？这与"批量操作 = 一条 op = 一次撤销"的既定语义有张力，**需要专门想清楚**
- ~~CLI 那边同样的问题：`kist import` 跑到一半 Ctrl-C 怎么办~~ ✅ **已定（2026-08-27）**：优雅停止，已完成的部分提交成**一条** op；第二次 Ctrl-C 才强制退出。配套定了导入幂等（同 folder 同 name 同 `blob_key` 就跳过），所以中断后重跑同一个目录是收敛的。详见设计文档 3.7.1。**这只解决了 CLI 单进程的同步导入**——serve 侧的异步任务模型（进度、取消、续传、任务与 op 的关系）仍然全部未定

这是个不小的子系统，别低估。

### ~~B3. 并发与多进程~~ ✅ 已定（2026-08-27）

**结论：`kist.lock` 上一把作用域为「一次逻辑写操作」的 OS 咨询锁，加上读路径比一次 `MAX(ops.id)`。详见设计文档 2.7。**

读代码定的，过程中有四条事实推翻了本条原来的前提：

1. **SQLite 争用不是问题。** 导入的哈希和落盘全在事务外，只有最后写 op 那一下进事务（毫秒级），WAL 下读者又不阻塞。「库级锁用户体验差」这条指控因此站不住
2. **最严重的失效不是 tag 树，是投影目录名缓存。** 它过期会让 `boxes/` 静默多出一个目录，两份链接指向同一批文件。这个缓存原来在设计文档里根本没写，已补进 3.4.1
3. **版本号早就存在。** 3.12 定了「op ID 就是版本号」，所以缓存失效判断不需要发明新概念
4. **有一个事务外的读-改-写窗口**（导入的文件名分配 vs `files(folder_id, name)` 的 UNIQUE 索引），它的作用域比数据库事务宽，SQLite 自己的锁救不了——这是唯一真正需要一把锁的地方

**原倾向「CLI 检测到 serve 就走 HTTP API」被推翻**，理由写在 2.7 的否掉清单里：它为了修一个缓存问题给整个 CLI 上税，把 CLI 的发布节奏绑死在 API 完整度上，而「serve 在不在跑」这个检测本身比原问题还难做对。

**还没解决的（留给 B2）**：`scrub` 和 `repair` 不持锁，所以它们的结论是「这一刻的快照」而非「此后恒真」。这在 CLI 上是对的语义，但 serve 把 scrub 做成后台任务之后，「报告什么时候算过期」需要在任务模型里有个说法。
