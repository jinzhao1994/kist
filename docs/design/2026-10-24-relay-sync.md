# 多级离线同步

2026-10-24 获授权实施。本文补充 [离线客户端设计](2026-10-21-offline-client.md)，不改变主库唯一最终权威的约束。

## 场景与范围

旅行期间手机以笔记本为上游；笔记本是主库的客户端。笔记本接收两端的临时增量，回家后合并回主库。单个客户端只有一个上游，拓扑为树；不实现多父节点、循环同步、自动选主或独立主库合并。这里的“手机”指协议角色，本阶段不等于实现原生手机应用。

## 两种确认

主库 `SyncResult` 继续表示正式写入，包含主库 op ID。新增独立的 `RelayReceipt` 表示某客户端持久接收，包含资料库 ID、中继 ID、原始 proposal ID、digest 和接收时间，**没有主库 op ID**。收到中继回执不能显示为主库已同步，也不能把相应操作变成最终确认。

proposal 的 ID、发生时间、payload、依赖、撤销和操作组引用端到端不变。中继接收时间只记录传输保管事实，不改变操作时间，不新增设备来源枚举。重试必须比较 ID 和 digest，重复接收返回原回执。

沿用客户端 `pending/` 和 `local-blobs/`，不新增临时主库。中继先验证新原文件的完整 hash 和大小，再校验并追加原始 proposal，最后追加保管回执；两个日志步骤均持久化后才回复。中途失败属于结果不确定，可用原请求重试。`pending_custody` 使用载荷版本 3，旧程序拒绝未知版本，不静默忽略保管信息。派生数据库不保存唯一回执。

保管回执不移出待提交队列。未确认的新原文件留在 `local-blobs/`，不受缓存时间和体积逐出影响。只有已下载的主库正式目录能证明主库拥有相应内容，继续沿用现有 AdoptConfirmedOriginals 边界。

## 两层目录与结果

主库确认目录与中继临时增量必须分别交换。主库目录仍按原 `SyncBoundary` 和正式 op ID 追赶；临时增量按稳定 proposal 身份和中继日志游标交换，不能混入正式目录或伪造连续主库 ID。

中继接收后继续复用现有待提交队列、冲突校验和主库幂等提交。下游应能获知仍待提交、正在提交、冲突、被放弃、被替换、主库已确认等结果。替换返回新 proposal 身份及理由，不改写旧意图。主库目录中的原始同步身份也可恢复丢失的正式回执，或识别经另一条路径已提交的操作。

下游的中继回执尚不是正式回执；下游后续的依赖和撤销引用继续用 LocalID，最终由主库按原有规则转换。不能用中继物化视图里的临时序号作为可传播引用。

## 双层交换的具体约束（2026-10-24）

第一版采用**固定版本的分页快照**交换中继 pending 视图。版本同时绑定已发布的主库边界、中继节点 ID、中继日志位置及校验和、条目数。主库目录仍按正式 op ID 增量下载；中继快照仅包含意图和结果，不包含原文件，不复制请求去重等内部记录。无变化时不追加本地日志。暂不引入增量补丁压缩：替换会调整逻辑位置，完整快照更容易校验断线后的依赖和终态；分页和固定版本保留未来优化的协议边界。

分页进入 pending 的版本 4 `pending_relay_page` 事件；未收齐时只推进传输游标，旧的完整视图继续可用。本机可继续追加自己的操作。收齐后先在临时数据库校验主库回执和重放，再追加最后一页、发布视图。断线重试比较已收页面，不能用相同版本替换内容。恢复依赖日志，不依赖 client.db。

完整视图按照“正式主库前缀 → 上游完整临时视图 → 尚未交付的本机操作”重建。原始 proposal 不变，独立修改不兼容时呈现冲突，不按时间覆盖。上游增量有独立保管标记，不能冒充本机新增内容再次向主库提交；本机提交至中继使用版本 3 `pending_relay_ack` 保存远端保管回执，仍不算正式确认。

下游把本机增量交给上游后，其放弃和替换决定由该上游协调，随后随快照传回，避免两端各自改变同一意图。依赖已被上游接收的操作可继续提交，LocalID 不改写。多层中继导出统一的逻辑视图，不把内部嵌套日志封装不断传给下一层。

更换节点要求先与原上游取回所有已交付操作的最终结果，未确认保管、结果不确定或未完成的快照传输会阻止切换。已完成的分支通过 `pending_relay_reset` 日志解除绑定，旧意图与回执仍保留；同节点换址保留临时分支。暂不支持把尚未确认的临时分支迁移到另一个中继，避免原上游与新上游同时决定冲突结果。

## 连接与安全边界

保持资料库 ID 校验和完整已知正式历史校验。新协议还需稳定节点身份、上游祖先链与临时增量边界校验，拒绝自连及环。换上游必须处理未确认分支和不确定提交，不能复用只有 URL 更新的路径。

中继使用自己的、可撤销的下游访问凭据，不能把主库令牌转交下游。现阶段凭据可访问该资料库的同步内容，与现有单库凭据一致；文件级分享权限仍属另一个议题。HTTP 暴露前必须接好鉴权、能力协商、续传和资源读取，不先开放一个无鉴权的临时提交端点。

## 实施顺序与验收边界

1. 持久接收及结果查询：独立保管回执、原件验证、转交现有主库提交队列、重试与重建测试。
2. 双层目录交换：导入中继增量、结果追赶、下游发送状态、依赖及撤销贯通，多层与直连切换测试。
3. 连接协议：节点身份、祖先链与防环、凭据、HTTP 接口和断点续传、缓存资源路径。
4. UI：明确“已交给远端，待主库确认”，复用现有设置与同步页组件；操作数量不混淆两层确认。
5. 三实例验收：离线双端修改、联网合并、丢回包重试、冲突及替换下传、主库直连去重、原件保护、重启与删库重建。

每一阶段独立验证；第 1 阶段通过不表示用户已能把客户端用作上游。端到端功能必须在第 5 阶段通过后才算完成。

## HTTP 与配置入口（2026-10-24）

客户端现在提供带独立凭据的同步接口；设置页同时提供「连接」和「访问凭据」，后者管理连接本机的下游，不复用上游令牌。原文件上传复用已有校验分块续传，读取优先使用本地受保护原件和缓存，缺少时按当前上游按需取回；预览同样逐层缓存。

连接验证保存 `client.parent_id` 和 `client.ancestors` 到 kist.toml。每次同步校验节点身份，同库不同节点不能通过替换地址偷偷接管。在线能力查询沿上游验证祖先链；上游不可达时可使用已保存链继续提供离线中继。请求携带节点经过链，重复节点或超过 32 层即拒绝，避免祖先记录过期后递归请求不终止。

自动同步沿用只自动处理单向变化的规则。中继上传带原子快照版本条件；遇到远端并行修改时暂停等待手动合并。每轮自动上传一个意图并取回最新快照，剩余意图由后续检查继续提交。保管确认在侧栏、同步页和本机历史中显示为「待主库确认」，不计入尚待上传数量，也不显示为已完成主库同步。
