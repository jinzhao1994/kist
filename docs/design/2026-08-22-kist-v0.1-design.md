- 日期：2026-08-22
- 状态：待评审
- 范围：v0.1（单用户、纯本地、"存得进、找得到"）

## 0. 概述

### 0.1 kist 是什么

一个自部署的个人归档应用。基本单元是 **box**（一次活动、一段经历、一批档案），配合一棵全局 **tag** 树做正交检索。既装照片视频，也装证件合同报告。

核心洞察：**归档位置和检索维度是正交的两件事。**

- **box 回答"这份文件是怎么来的"** —— `2019-08-12_办护照`
- **tag 回答"这份文件是什么"** —— `证件/护照`
- **metadata 回答"它现在什么状态"** —— `user:有效期 = 2029-08`（v0.2）

一次看病包含挂号单照片、检查报告 PDF、处方、报销凭证——现有工具会把它拆散：Immich / Nextcloud Memories 只有时间轴和人脸，放不下 PDF；Paperless-ngx 的文档归档做得好但没有"事件"概念；Seafile / FileBrowser 是纯目录树，tag 是二等公民。

### 0.2 v0.1 解决什么

**把真实数据塞进去，并能找出来。** 单用户、纯本地、无登录、无分享。

验收标准：作者本人能把自己的照片和证件迁进去，并且信得过（数据完整性可验证、误操作可撤销）。

### 0.3 v0.1 明确不解决

分享与访问控制、SSO、对象存储冷层、内网穿透、OCR、多设备同步、人脸/相似图检测。范围外清单见第 8 节。

### 0.4 核心决策速览

| 决策 | 结论 |
|---|---|
| 语言与分发 | Go + 单二进制，前端产物 embed |
| 元数据存储 | SQLite（`modernc.org/sqlite`，纯 Go）。**DAL 为 Postgres 留好接口，v0.1 不实现** |
| box 层级 | 顶级、扁平、不可嵌套 |
| box 内目录 | Folder 一等实体（非路径字符串），允许空目录，深度上限 32 |
| `updated_at` | 逐层向上传递到 box；取 `ops.ts`；仅"用户意图"的 op 传递 |
| 文件归属 | 恰好属于一个 box |
| tag | 实例内全局的一棵树，运行时常驻内存；folder 不可挂 tag |
| tag 来源 | `file_tags.source`（user / derived）+ 独立的 `tag_rejections` 抑制名单 |
| 库模式 | 接管（kist 拥有库目录） |
| 历史模型 | append-only `ops` 表 + 可重建的物化视图 |
| 权威数据 | **只有 `ops` 表 + `blobs/` 目录**，其余全部可重建（含 `blobs` 表） |
| GC | v0.1 不做，保留期 = 永久（什么都不销毁） |
| 重建确定性 | `Apply` 是纯函数：不生成 ID、不读时钟、不做状态相关决策 |
| op 判别 | `action` 存 TEXT（历史行必须永远可读），类型安全放 Go 侧 |
| op 来源 | `source` 开放枚举：user / extractor / maintenance / sync |
| op payload | Go 侧 typed struct；DB 侧不透明 JSON。要查的东西一律提成列或索引表 |
| 撤销 | 追加反向 op；从 HEAD 反向重放，默认上限 1000 步 |
| blob | 内容寻址（SHA-256）、不可变、0444 |
| `boxes/` 目录 | 人可读的**投影**，可整棵重建 |
| 外部改动 | 假设不发生；`boxes/` 被改坏就重建，权威数据受保护 |
| v0.1 检索 | LIKE 全扫（tag 走内存），倒排索引押后 |
| 后端框架 | 无框架，stdlib `net/http` + Huma v2（自动生成 OpenAPI） |
| SQL 层 | `sqlc` 生成类型安全代码，**不用 ORM** |
| Web UI | React + TypeScript + Vite + Tailwind |
| 手机端 | 先做 PWA；原生 app 等自动备份成为优先级再说 |
| 许可证 | Apache-2.0 |

## 1. 概念模型

### 1.1 三条轴

```
Box  ──── 顶级容器，扁平，不可嵌套。文件恰好属于一个 box。
Tag  ──── 实例内全局的一棵树。box 和 file 都可挂任意多个 tag 节点。
Metadata ─ 键值事实，带命名空间与来源。v0.1 只做 extracted 侧。

Folder ── 不是一条轴，是 box 内部的组织结构。一等实体，见 1.4。
```

**为什么 box 扁平。** 一旦 box 可嵌套，每次建 box 都要先回答"它该挂在哪个父 box 下"，而现实里「2024 家庭出游」和「云南行」的父子关系是含糊的。扁平之后这个焦虑消失，跨 box 的归组交给 tag 树（`出行/家庭/2024`）。

**为什么没有 `kind` 枚举。** 早期设计想用 `kind = 活动 | 常设集合` 区分「云南行」和「证件与档案」。但既然归档位置与检索维度正交，"这个 box 是不是真的是一次活动"就不重要了——`start_at` 填了就上时间轴，没填就不上，比枚举少一个概念、多一份信息。

**为什么证件能放进 box。**「办护照」本身就是一次活动。而"我现在的护照在哪"这个查询根本不走 box，它走 `tag=证件/护照` + `有效期 > today`。没有办理记忆的老证件（出生证、旧房产证）扔进一个 `早年杂档` box 也自洽。

### 1.2 命名说明

| 名字 | 为什么不用别的 |
|---|---|
| **Box** | 不用 `Event`：软件语境里 `Event` 强指事件总线 / event sourcing，而这里它是个容器；日历里的 event 还是"未来某时刻的日程"，时态也错。不用 `Activity`：Android 核心类名 + activity feed 双重占用。不用 `Case`：`case` 是 Go 关键字。选 Box 是因为它呼应 kist（苏格兰语"箱子"）——kist 是柜，box 是柜里的盒——且中性到能同时装「云南行」和「护照」 |
| **Tag** | 不用 `Label`：K8s / Docker 的 label 是 key=value，会和 metadata 这条轴撞车。"tag 是树形的"由 UI 承担表达，不需要名字来背 |
| **Metadata** | EXIF 那些**文件固有**元数据和用户自定义字段收进同一个键值空间，靠命名空间区分。这样检索面统一（"光圈 < 2.8"、"iPhone 15 拍的"、"三个月内到期"走同一套索引），UI 只有一个面板 |

### 1.3 Box

```
Box {
  id          UUIDv7
  name        TEXT              -- 用户可见的真名（不做平台净化）
  description TEXT
  created_at  TIMESTAMP (UTC)   -- 取自 ops.ts，非 time.Now()，见 2.3.1
  updated_at  TIMESTAMP (UTC)   -- 系统写
  start_at    LocalDateTime?    -- 用户填，活动实际发生时间，变精度
  end_at      LocalDateTime?
}
```

**为什么 start/end 不带时区、不转 UTC。** 它们描述的是人的时间——"2019-08-12 在云南"就是那天。转成 UTC 会让旅行少一天。而 `created_at` / `updated_at` 是机器时间，存 UTC。

**变精度日期（EDTF 风格）。** 你可能只记得"2015 年"，也可能精确到分钟。存 ISO-8601 前缀字符串 + 精度枚举：

```
"2019"              precision=year
"2019-08"           precision=month
"2019-08-12"        precision=day
"2019-08-12T14:30"  precision=minute
```

这套方案的关键性质：**ISO-8601 前缀按字符串排序就是按时间排序**（`"2019" < "2019-08" < "2019-08-12" < "2020"`），不需要任何特殊比较代码，两个数据库都能直接排序和做范围查询。

精度必须知道，因为显示时要诚实——只知道 "2019-08" 却渲染成 "2019-08-12" 是在编造信息。

**但精度不单独存一列。** 第一版设计里有 `start_prec` / `end_prec` 两个枚举列，去掉了：精度**完全由字符串长度决定**（4 / 7 / 10 / 16），存成独立列就多了一个能和字符串打架的真相来源。而"同一个事实有两个存储位置"正是不变量 4 反对的形状——一旦某条写入路径漏更新其中一个，DB 里就出现 `"2019"` 配 `precision=day` 这种自相矛盾的行，且没有任何约束拦得住。

做法：**Go 侧的 `LocalDate` 类型带 `Precision` 字段，解析字符串时推导出来；DB 只存字符串。** 一个 `switch len(s)` 换掉两列和两条必须人工维护的一致性约束。

代价是 SQL 里筛"只精确到年的 box"要写 `length(start_at) = 4` 而不是 `start_prec = 'year'`——但 v0.1 没有这个查询，将来真要也只是加个函数索引。

不强行约束到月精度，因为：① 婚礼、体检、看病本来就精确到某一天；② 砍到月并不能消除变精度问题，你依然会遇到"只记得是 2015 年"。

### 1.4 Folder

box 内部的层级结构。**是一等实体，不是文件上的路径字符串。**

```
Folder {
  id         UUIDv7
  box_id     UUIDv7            -- NOT NULL
  parent_id  UUIDv7?           -- NULL 表示该 box 的根
  name       TEXT              -- 根 folder 的 name 为 ""
  created_at TIMESTAMP (UTC)   -- 取自 ops.ts，见 2.3.1
  updated_at TIMESTAMP (UTC)
  UNIQUE (parent_id, name) WHERE parent_id IS NOT NULL   -- 见下
  UNIQUE (box_id)          WHERE parent_id IS NULL       -- 每个 box 恰好一个根
}
```

**每个 box 创建时自带一个根 folder 行**（`parent_id = NULL, name = ""`），而不是让 `File.folder_id` 可空来表示根目录。理由是可空外键会让唯一约束失效——SQL 里 NULL 互不相等，`UNIQUE(box_id, folder_id, name)` 对根目录下的文件**根本不会触发**。这正是那种在 SQLite 和 Postgres 上都"看起来能跑"、实际两边都漏的坑。

**同一个坑在 folder 自己身上又踩了一次**，所以上面写成两条部分索引。朴素的 `UNIQUE(parent_id, name)` 对根 folder 无效——它们的 `parent_id` 全是 NULL，NULL 互不相等，于是**同一个 box 建出两个根目录不会被任何约束拦住**，而那会让整棵投影树分叉。拆成"非根管重名 + 根管唯一"两条部分索引之后，两种情况都真的有约束。两个引擎都支持带 `WHERE` 的部分索引。

**tag 树本来有完全相同的问题**（根 tag 的 `parent_id` 也是 NULL），但它走了另一条路——tag 名全局唯一，见 1.6。folder 不能照搬：文件名重名是完全正常的（每个 box 底下都有 `发票/`），而 tag 重名不是。

**为什么目录必须是一等实体，而不是文件上的 `folder_path` 字符串：**

1. **和设计其余部分一致。** tag 树就是 `parent_id` + "非空则拒绝删除"，folder 用同一套形状。而前缀字符串是一套独立的逻辑，在这份设计里是异类
2. **`Inverse` 要小且精确。** 整个 op log 建立在"每个操作可撤销"上。一等实体的改名/移动是改一行，`Inverse` 天然精确；前缀模型的改名要靠"禁止合并"这条人为限制才能让 `Inverse` 成立——那是把复杂度推给用户
3. **空目录成立。** 前缀模型下，删掉最后一个文件目录就消失了，"先建好结构再分批导入"这个工作流根本做不到；导入源里的空目录也会被静默吞掉
4. **拦得住幽灵目录。** 前缀模型下 `发票/` 和 `发票 /`（尾部空格）是两个不同目录，没有任何东西会拦住打错的字

**为什么不能干脆砍掉目录**（考虑过这个更激进的简化）：导入时的重名冲突。`Day1/IMG_001.jpg` 和 `Day2/IMG_001.jpg` 拍平进同一个 box，唯一约束会强制自动改名，把源数据的结构信息碾掉。

**为什么不学 Linux 把目录做成一种特殊文件。** Unix 的优雅在于"一切皆 inode"，但在关系模型里把 File 和 Folder 合成一张表加 `kind` 列只有代价：每个文件查询都要带 `WHERE kind='file'`（污染面和被否掉的 `deleted_at` 一样）、`blob_key` 必须可空、唯一约束语义变模糊。而我们不需要任何 POSIX 语义（目录硬链接、`.`/`..`、权限位）。

**配套规则：**

- **删除非空目录直接拒绝**，与 tag 策略一致。要删先移走内容，或显式选择"连同内容一起删"（那是另一种 op，payload 明确）
- **深度上限 32 层**，性质是"防病态输入的兜底"，正常使用碰不到。深度对模型没有成本——`parent_id` 链遍历是 O(depth)，而 folder 本来就按 box 整批加载
- **真正的检查是投影路径长度，不是层数。** 用层数近似长度是在约束错误的量：八层每层 15 字符就用光了 Windows 的额度，但目录名都是两三个字时二十层也塞得下。检查是平台相关的——Windows 上投影路径超过约 250 字符就**告警**（说明这些文件在资源管理器里可能打不开），Linux / macOS 阈值高得多。**告警而非拒绝**：数据照存，只是明确告知；`kist verify` 也报这一项。kist 自身不受此限，Go 在 Windows 上用 `\\?\` 前缀可达 32767
- **folder 不可挂 tag**，理由见 1.6.2（认真考虑过继承方案，否掉了）

### 1.5 File

```
File {
  id          UUIDv7
  box_id      UUIDv7            -- 恰好一个，NOT NULL。冗余但必要，见下
  folder_id   UUIDv7            -- NOT NULL（根目录也是一个 folder 行）
  name        TEXT
  blob_key    TEXT              -- → blobs.key
  captured_at LocalDateTime?    -- 从 EXIF 提取
  created_at  TIMESTAMP (UTC)   -- 取自 ops.ts，见 2.3.1
  updated_at  TIMESTAMP (UTC)
  UNIQUE (folder_id, name)
}
```

**`box_id` 是冗余的**（folder 已经知道自己属于哪个 box），但必须有——`Query.Boxes` 是最热的筛选路径，没有它每次按 box 筛都要 join `folders`。

代价要说清楚：**因此"跨 box 移动一个目录"是 O(n)**，要改所有子文件的 `box_id`。这个取舍是热路径优先，而跨 box 移动目录很罕见。**box 内的改名和移动仍然是 O(1)**，那才是常见操作。

不变量：`file.box_id == folder(file.folder_id).box_id`。由 `library` 保证，`kist verify` 复核。

**唯一约束是必须的**，因为 `boxes/` 要投影成真实文件系统，而真实文件系统本来就不允许同目录同名。导入时冲突自动改名 `发票 (2).jpg`。

**不做 `deleted_at` 软删除标志位。** 加了它每个查询都要带 `WHERE deleted_at IS NULL`，污染面太大。回收站从 ops 渲染（`kind='delete'` 且在保留期内），还自带时间和批次信息。

### 1.5.1 `updated_at`：逐层向上传递的"这底下最近有动静"

`box` / `folder` / `file` 三者都有 `updated_at`，语义统一：

> **任意相关修改，并逐层向上传递到父目录直至 box。**

也就是说，一个目录的 `updated_at` 反映的是**它整棵子树**最近一次被改动的时刻。这样在 `boxes/` 里逐层往下翻时，一眼能看出该往哪个目录钻。

注意这个字段**不是**为了回答"内容什么时候变的"——那个问题 `blob_key` 比对 + op log 已经能答，不需要立列。它存在的唯一理由是**子树聚合**，而那是 op 表推导不出来的（要对每个目录做一次子树扫描）。

以下四条是实现约束，漏掉任何一条都会出错：

**① 时间戳取 `ops.ts`，不取写入时的墙上时钟。**

`kist rebuild` 要从 ops 重放重建物化视图。如果重放时写"当前时间"，重建出来的库里所有 `updated_at` 都会变成重建那一刻——**整个字段被抹平**。取 `ops.ts` 则重放是确定性的，且天然单调递增。

**② 只有"用户意图"的 op 才传递。**

最容易漏的一条。升级 EXIF 提取器后跑一次全库重新提取，如果那算"相关修改"，**十年的归档会在一瞬间全部变成"刚刚修改"**，字段直接作废。

| 传递（`source=user`） | 不传递 |
|---|---|
| 导入、删除、改名、移动 | 重新提取 metadata（`source=extractor`） |
| 打 / 去 tag | 重新生成缩略图 |
| 编辑 metadata（user 侧）、编辑 box 字段 | `relink` / `rebuild` / `gc` / `scrub`（`source=maintenance`） |
| 建 / 删 / 改目录 | |

一句话：**`updated_at` 记录人的意图，不记录系统的活动。** 由 `ops.source` 承载这个区分（见 2.2）——它是个开放的枚举而非布尔，因为将来自动执行的来源不止一种。

**③ 传递按 op 批量做，不按文件逐个做。**

朴素实现会退化：导入 5000 个文件，逐个走祖先链就是 5000 × 深度 次更新。正确做法是在一条 op 内先求出受影响祖先的**去重集合**，每个只更新一次：

```
导入 5000 个文件到一个目录
  → 5000 行 files
  → 该目录 + 祖先链（约 3-4 行 folders）   ← 各更新 1 次
  → 1 行 boxes
```

跨 12 个 box 批量打 tag 的 500 个文件同理：500 行 + 约 50 个去重目录 + 12 个 box。写放大很小，**前提是别写成逐文件循环**。

**④ `updated_at` 不参与 `Inverse`。**

撤销 op 47 之后，`updated_at` 应是撤销发生的时刻，而不是恢复成 op 47 之前的值——撤销本身也是一次改动。所以它是**被维护的派生状态，不是语义状态**：不进 op payload，不需要写 `Inverse`。

**连带效果：**

- `box.updated_at` 直接就是"最近有活动"，用于 box 列表排序
- 投影时可以 `os.Chtimes` 把 `boxes/` 下目录的 mtime 设成这个值，这样在 Finder / 资源管理器里按修改时间排序也有意义，而不是"全部都是 relink 那一刻"

### 1.6 Tag

```
Tag {
  id        UUIDv7
  parent_id UUIDv7?
  name      TEXT
  name_fold TEXT              -- Go 生成的折叠形式（NFC + ToLower），见 4.7
  UNIQUE (name_fold)          -- ★ 全局唯一，不按父作用域
}
```

**tag 名全局唯一，层级不构成命名空间。** 这是与 folder（`UNIQUE(parent_id, name)`）刻意的分叉。

考虑过的替代方案是按父唯一——即 `地点/云南` 和 `旅行/云南` 可以共存。否掉，三条理由：

1. **它会毁掉"移动子树 O(1)"这个性质。** 把 `云南` 移到一个已有 `云南` 的父节点下会撞名，于是移动 op 必须长出重名处理：自动改名会让 payload 从 `{node, old_parent, new_parent}` 膨胀成还要记改名前后，`Inverse` 也跟着变复杂；拒绝则要在移动前查一遍。全局唯一之下名字根本不参与移动，那个三字段 payload 就真的够了
2. **同名 tag 在 UI 上分不清。** `file_tags` 上的 tag chip 只有名字，同名之下必须一路带路径渲染（`证件/护照`、`扫描件/护照`），否则用户看到两个一模一样的 chip
3. **多面分类的正确答案是挂多个 tag，不是建镜像子树。** `原件/护照` 和 `复印件/护照` 应该是 `护照` + `原件` 两个 tag 的组合。按父唯一等于默许镜像子树，那是会慢慢长歪的方向；全局唯一把用户推回设计意图上

**唯一性建在 `name_fold` 而不是 `name` 上。** 否则 `Apple` 和 `apple` 会是两个 tag，"唯一"就成了骗人的。折叠函数与 4.7 的搜索折叠是同一个，由 Go 拥有。

**看起来会疼、实际不疼的一处：`其他` / `未分类` 这类通用叶子名。** 全局唯一之下不能在 `地点` 和 `人物` 底下各挂一个。但**根本不需要**——内部节点自己就能挂文件，"是个地点但没细分"直接挂 `地点` 即可；而按 4.3 的语义筛 `地点` 本来就含全部后代，这类文件自然落在结果里。多建一个 `其他` 子节点只是把同一件事说两遍。

真正剩下的代价只有一种：**两个语义确实不同的概念恰好同名**（人名与地名撞、品牌与设备厂商撞）。这种情况罕见，且解法就是把名字起得更具体一点——对一份要在十年后还看得懂的归档来说，那本来就是更好的名字。

**没有物化路径列。** tag 树只有几千个节点，运行时整棵常驻内存，求后代是一次内存遍历（微秒级）。`path` 列只服务于"解析后代 ID 集合"这一步，而内存做得更快更简单。

砍掉它还白赚一个简化：**移动 tag 子树在 DB 里是 O(1)**（只改一行 `parent_id`），不用级联重写子树路径，对应的 op payload 也从"一堆受影响节点"缩成"一个节点、旧父、新父"。

**内存树同时缓存每个节点的直接挂载文件数**，含后代的总数在树上向上汇总（tag 选择器里 `人物 (1,204)` 这种显示）。启动时一次 `SELECT tag_id, COUNT(*) FROM file_tags GROUP BY tag_id` 拉全量，之后由 `library` 在 apply op 时增量更新。不在 `tags` 表上加冗余列——重启就重新推导，没有漂移风险。

**前提假设：内存树的一致性依赖「`library` 是唯一写入口 + 单进程」。** 这条在 kist 还只是 CLI 时自动成立，`kist serve` 一出现就破了——解法见 2.7，一次 `MAX(ops.id)` 的比对。真正需要**失效通知**的是多进程共享一个 Postgres 的场景（官方后端），那时要改的远不止这一处，不预留。

**删除 tag 的策略：有子节点或有文件挂着就直接拒绝**，要求用户先显式处理。级联删除在归档软件里太危险——一次误点可以静默毁掉全库分类信息，撤销它的 op payload 也会大到离谱。

#### 1.6.1 tag 的来源与用户否决

`file_tags` 带来源，另有一张独立的否决表：

```sql
file_tags (
  file_id, tag_id,
  source  ENUM(user | derived),     -- 谁加的
  PRIMARY KEY (file_id, tag_id)
)                                    -- 一行就是"有这个 tag"，没有例外

box_tags (                           -- box 也能挂 tag，见 1.6.2
  box_id, tag_id,
  source  ENUM(user | derived),
  PRIMARY KEY (box_id, tag_id)
)

tag_rejections (                     -- 用户明确否掉的自动推导
  file_id, tag_id,
  PRIMARY KEY (file_id, tag_id)
)
```

`box_tags` 与 `file_tags` 形状相同但**必须是两张表**：`file_id` 和 `box_id` 指向不同实体，合成一张 `(target_type, target_id)` 宽表会让外键失效（指不了两张表），而外键是这里唯一能拦住悬挂引用的东西。`tag_rejections` 只对 file 有——否决机制服务于提取器，而提取器产出的是文件级 tag。

**为什么否决要独立成表，而不是在 `file_tags` 上加状态位。** 加 `state = present | rejected` 会让每个 tag 查询都要带 `WHERE state='present'`——与被否掉的 `deleted_at` 是同一种污染，而 tag 筛选是最热的路径。独立成表后 `file_tags` 保持"有行即有 tag"的干净语义，否决表只在提取器管线里被查询，且天然很小（只有"自动推导错了且用户纠正过"才进）。

**这条规则是 1.7 metadata 那条规则的另一半。** 那条只保护了用户**写入**的东西（重扫不覆盖 `source=user`），但没保护用户**删除**的东西——删除同样是用户意图，不留痕的话下次重扫就复活了。将来 OCR / 小模型打标一定会出错，这个洞必须堵上。

**四条配套规则：**

1. **提取器只拥有 `source=derived` 的行**，可增删改；**永不触碰 `source=user`**。与 metadata 完全对称
2. **写入前先查否决表**，命中就跳过。这是整个机制的作用点
3. **删除 `source=user` 的 tag 不产生否决记录**——没有任何东西会把它加回来。只有删 `derived` 的才留痕，这让否决表保持很小
4. **手动添加一个曾被否决的 tag，要清掉否决记录**，且该行 `source=user`（此后提取器再也动不了它）。显式操作覆盖历史否定

否决动作本身是一条 op（`source=user`），可审计、可撤销。

**命名注意：不要叫"负向 tag" / `negative_tags`。** 那个名字暗示它参与查询语义（像 `NOT tag=隐私`），会引诱后来的人把它做成可筛选的东西。它不是——**它只是提取器的抑制名单**。

**v0.1 范围：** 没有任何东西会自动推导 tag（M3 的 `extract` 只产出 EXIF metadata，tag 建议要到 v0.3）。所以 `file_tags.source` 现在就加（全部是 `user`）、`tag_rejections` 现在建表但空着，**规则的执行等提取器真的开始产 tag 时再写**。

`source` 必须现在加而不是以后：等以后再加意味着要给存量行回填来源，而那个信息届时已无从判断。

**已知的平行问题：** v0.2 开放 `user:` metadata 编辑时会遇到一模一样的情况（AI 写的 `ai:caption` 错了，用户删掉，重扫又回来），届时应当用同一个答案。

#### 1.6.2 folder 不可挂 tag

可挂 tag 的实体只有 **box** 和 **file**。

考虑过让 folder 也能挂 tag、并**隐含传递给子树**（"目录有 tag 相当于其子节点全部隐含该 tag，读取时放大"），动机是减少 `file_tags` 行数。否掉，理由按重要性排序：

**① 省下来的东西量化后不存在。** `file_tags` 就是两个 UUID。十万文件 × 平均 3 个 tag = 30 万行 ≈ 30–90 MB，而同一个库的 `derived/` 是几个 GB、原图是几百 GB。为几十兆换一套继承语义，性价比是负的。（顺带：**UUID 存 BLOB(16) 而不是 36 字符 TEXT**，这一条本身就比继承机制省得多。）

**② 摘不掉。** 给 `发票/` 打 `财务`，里面有一张其实是照片——无法单独去掉它的 `财务`，除非引入负向 tag，那既是新概念又把想省的行写了回来。这是继承类设计的经典结局：NTFS ACL 继承、Google Drive 文件夹共享、S3 bucket policy，无一例外都长出了覆盖机制。

**③ 移动文件会静默改变分类，且历史里看不出来。** 文件从 `发票/` 拖到 `照片/`，悄悄丢了 `财务`、获得了新目录的全部 tag。op log 记的是"移动"，**没有任何一条说"因此失去了 tag 财务"**。对一个以"完整历史 + 可回退"为卖点的系统，有效状态的改变不出现在审计日志里是硬伤。

**④ 查询与计数缓存都变复杂。** 每个 tag 条件从一次索引扫描变成"直接命中 OR `folder_id IN (被打标目录的全部后代)`"，且需要把整个 folder 森林也常驻内存（tag 树几千节点是有界的，folder 数量却随文件库线性增长）。1.6 那句启动时的 `GROUP BY` 计数也不再成立。

**真实诉求（"不想为 200 个发票点 200 次"）用批量操作解决**：一次操作物化 200 行 `file_tags`。用户感知的操作量一样，而查询、删除、历史、撤销全部保持简单。

也考虑过在 folder 上加 `default_tags`（落入该目录的文件自动打标，但写成真实行）。同样不做——自动打标的职责已经由提取器承担（1.6.1），再加一条按位置推导的路径是多余的概念。

### 1.7 Metadata（v0.1 只做 extracted 侧）

```
Metadata {
  target_type  ENUM(box|file)
  target_id    UUIDv7
  key          TEXT              -- 带命名空间
  value        TEXT
  source       ENUM(extracted|user)
}
```

命名空间：

```
exif:Make        = "Apple"        source=extracted
exif:FNumber     = 1.78           source=extracted
file:size        = 4823901        source=extracted
file:mtime       = 2019-08-12…    source=extracted
ocr:text         = "…"            source=extracted   (v0.3)
ai:caption       = "…"            source=extracted   (v0.3)
user:有效期       = 2029-08-12      source=user        (v0.2)
```

**两条硬规则：**

1. **key 必须带命名空间。** 否则用户建一个叫 `Make` 的字段就和 EXIF 的 `Make` 撞了。
2. **重新扫描只覆盖 `source=extracted`，永不触碰 `source=user`。** 没有这条，任何一次重建索引都会把手填的护照有效期洗掉。

**`file:mtime` 值得专门一提：** 对 PDF、扫描件、录音这类没有 EXIF 的文件，**源文件修改时间往往是唯一可用的时间信号**，比导入时间有意义得多。捕获成本为零（`os.Stat` 就有），但丢了就再也拿不回来——导入时必须抓。

**规模控制：** EXIF 有几百个 key，全展开会让一张照片占 100+ 行。做法是白名单常用键进 kv 表（可索引），原始 EXIF 整包存 JSON 一列（可查看不可索引）。

**v0.1 不做的：** `user:` 侧的写入 UI、tag 节点携带 schema、metadata 上的搜索。表结构就位，功能留空。

## 2. 架构内核：op log

### 2.1 CQRS 拆分

系统里有两类数据，形状完全不同，必须分开：

```
ops                        ← 纯 append，永不修改，历史的唯一真相
  ↓ 物化
boxes / files / tags /     ← 当前状态视图，普通行、普通 UPDATE/DELETE
file_tags / metadata          因为它 100% 可从 ops 重建
```

**为什么不用双时态（每行带 valid_from / valid_to）。** 那样每个查询都要带版本谓词，索引复杂度上升，而且"修改 = 关闭旧行 + 插入新行"这条别扭约束会贯穿每一行数据层代码。而 `valid_to` 本身是个 UPDATE，和"append-only"自相矛盾。

**为什么不用"纯 append + 查询取最大版本"。** 谓词必须在按实体去重之后才能应用（否则会匹配到"曾经在 box B 里"的旧行），这废掉了所有筛选列上的索引。而 kist 的核心卖点就是筛选。

拆分之后两边各自变干净：

- **当前状态表零版本字段**，`SELECT * FROM files WHERE box_id=? AND ...` 就是普通 SQL，索引完全生效。这是 99% 的查询
- **`ops` 表是真正的纯 append**，一次 INSERT，没有任何 UPDATE
- **写入更简单**：一个事务内插一条 op + 几条普通 UPDATE
- **物化视图坏了不是数据丢失**：`kist rebuild` 从 ops 重放重建

**权威数据只有两样，而且跨越了 DB 与文件系统的边界：**

```
ops 表         ← 历史的唯一真相
blobs/ 目录    ← 内容的唯一真相
```

`kist.db` 里除 `ops` 外的**每一张表**都可重建：

| 表 | 从哪重建 |
|---|---|
| `boxes` / `folders` / `files` / `tags` / `file_tags` / `tag_rejections` / `metadata` | 重放 ops |
| `op_boxes` / `op_files` | 从 `ops.payload` 提取（见 2.2.1） |
| `blobs` | **扫 `blobs/` 目录**——`key` 就是文件名，`sha256` 在 `key` 里，`size` 是 `os.Stat`。这张表没有一个字段是不可重建的 |

这条不变量是 `kist rebuild` / `kist relink` / `kist verify` 三个命令成立的共同前提，也是"物化视图损坏不等于数据丢失"这个安全性质的来源。

### 2.2 ops 表

```sql
ops (
  id          INTEGER PRIMARY KEY,      -- 单调递增，即版本号
  ts          TIMESTAMP (UTC),
  action      TEXT NOT NULL,            -- import_files / move_files / add_tags /
                                        -- create_folder / rename_folder / …
  source      TEXT NOT NULL,            -- user | extractor | maintenance | sync
  actor       TEXT,                     -- 谁（v0.2 分享后才有多值）
  payload     JSON NOT NULL,
  reverts_id  INTEGER REFERENCES ops(id)
)

op_boxes (                           -- 一条 op 碰过哪些 box
  op_id   INTEGER,
  box_id  UUIDv7
)

op_files (                           -- 一条 op 碰过哪些 file
  op_id   INTEGER,
  file_id UUIDv7
)
```

**`action` 在 DB 层是 TEXT，不是 enum，也不加 CHECK。** 三条理由，第三条是决定性的：

1. SQLite 没有 ENUM 类型（只能 TEXT + CHECK），Postgres 有原生 enum 但加值要 `ALTER TYPE`——双实现立刻分叉，conformance suite 又多一处要对齐
2. op 种类是持续增长的开放集合（v0.1 约 15 种，做完分享/分层/OCR 会有四十多种），DB 层 enum 意味着每加一个功能就要一次 schema 迁移
3. **append-only 的历史表必须对未来宽容。** 假如某天重构掉一个 op 种类，历史行还在——而 Postgres enum 一旦删掉某个值，**那些历史行连读都读不出来**。对一个把"完整历史"当卖点的系统，这是灾难性的

分工是：**DB 列宽容，Go 侧严格。** `type OpAction string` + 常量集 + `map[OpAction]OpHandler` 注册表，读到未注册的 action 时报明确错误（「这个库是更新版本的 kist 写的」）而非崩溃。

**`source` 与 `actor` 是两条不同的轴：**

| | 含义 |
|---|---|
| `actor` | **谁**做的（哪个用户 / 设备 / token）。v0.2 有分享之后才会有多个值 |
| `source` | **什么性质的执行者**：`user`（人通过 UI/CLI）、`extractor`（提取管线）、`maintenance`（gc / relink / rebuild / scrub 的修复）、`sync`（远期，从另一台设备复制来的 op） |

`updated_at` 的传递规则是"`source` 属于某个集合"——v0.1 是 `{user}`，将来 sync 落地时变成 `{user, sync}`（它代表另一台设备上的人的操作）。规则住在 Go 里，改起来是一行。`source` 同样是 DB 存 TEXT、Go 侧 typed 常量。

**连带澄清：EXIF 提取本身也是一条 op**（`source=extractor`）。否则 `kist rebuild` 重放时拿不到 metadata，只能把每个 blob 重读一遍重新提取——重建会从几秒变成几小时。

**`reverts_id` 是列而不是 payload 字段**，因为它要被**热查询**：历史面板每次渲染都要问"这条 op 被撤销过吗"（`WHERE reverts_id = ?`），用来标记已撤销状态和防止重复撤销。塞进 JSON 就得靠 JSON 提取 + 表达式索引，而 SQLite 与 Postgres 的 JSON 函数名称和行为都不同——正是 4.7 里列为"必须逐条钉死"的那类分歧，不值得为一个普通列能解决的问题引入。

概念上也说得通：payload 描述"这条 op 对领域做了什么"，`reverts_id` 描述"这条 op 与另一条 op 的关系"——指向同一张表的外键，属于结构层而非内容层。稀疏 NULL 列在两个引擎里都几乎不占空间。

#### 2.2.1 payload 与索引表的关系

`op_boxes` / `op_files` **本质上是 `ops.payload` 的索引**，因此性质是派生的、可重建的——`kist rebuild` 要连它们一起重建。

**为什么不直接在 JSON 上建索引。** 20 万条 ops 的实测（SQLite 3.53.3）：

| | 结果 |
|---|---|
| **标量**字段表达式索引 `json_extract(payload,'$.box_id')` | ✅ 129.88ms → **0.04ms** |
| **数组**字段：`json_each` 展开后建索引 | ❌ `subqueries prohibited in index expressions` |
| **数组**字段：GIN | ❌ SQLite 没有 |
| 数组成员查询（`json_each` 展开，无索引可用） | 154ms，只能全扫 |

⚠️ 有个陷阱：`create index on ops(json_extract(payload,'$.box_ids'))` **会建成功**，但它索引的是整个数组的序列化字符串，只对"整个数组完全相等"有用，对成员查询毫无帮助——建了不报错，然后发现没走索引。

而我们需要的恰恰是数组成员查询（一条 op 碰多个 box / 多个 file）。真实查询形态「某个 box 的最近 50 条历史」（历史面板每次打开都跑）：

```
op_boxes 索引表 JOIN + ORDER BY + LIMIT 50   →    0.11 ms
json_each 全扫 + ORDER BY + LIMIT 50         →   94.63 ms      860 倍
```

且差距会随时间恶化：`ops` 只增不减，全扫代价线性增长，索引表是 O(log n)。

**关键在于两个数据库的能力在这里分叉。** Postgres 做得到（`jsonb` + GIN + `@>` 包含查询），SQLite 做不到。DAL 设计允许两个实现各写各的最优 SQL，但**不允许它们在渐进复杂度上分叉**——那样 conformance suite 只能测正确性、测不了"两边都能用"，SQLite 那边会随库变大慢慢烂掉。

况且即便在 Postgres 上也不如显式索引表：GIN 拿到的是匹配行的 bitmap，`ORDER BY op_id DESC LIMIT 50` 还要再排一次；而 `(box_id, op_id DESC)` 的 btree 直接就是有序的。

**提炼成一条原则**（它同时解释了 `reverts_id` 提成列、`op_boxes`/`op_files` 提成表这三个决定）：

> **payload 是不可查询的载荷。任何需要被查询的东西，必须提取成列或索引表。**

**payload 的类型化分两层：**

- **Go 侧必须是 typed struct**，每个 action 一个，由注册表里的 handler 负责编解码，**永远不出现 `map[string]any`**
- **DB 侧就是一个不透明的 JSON 列**。payload 在几十种 action 之间是多态的，做不成定型的列；而"一个 action 一张表"意味着几十张表加满地 join，更糟

**存储用 TEXT json 而非 jsonb。** 既然从不查进去，jsonb 的解析速度优势用不上，而**审计日志的人类可读性有真实价值**——历史坏掉时你想 `SELECT payload FROM ops` 直接读懂它。

**一个必须接受的冗余：** `op_files` 里有 500 行，payload 里也有那 500 个 file id，重复两份。这是必要的——payload 必须自足，否则 `Apply` 要读 `op_files` 才能执行，而 `op_files` 又要从 ops 重建，形成循环。不变量是：

> **payload 自足；每张索引表都必须能从 payload 单向重建。**

`op_files` 服务于**单个文件的完整历史**（M5 的版本链对比）——`updated_at` 只给"最近一次"，答不了"这个文件都经历过什么"。成本：批量给 500 个文件打 tag 会多写 500 行，与本来就要写的 `file_tags` 同量级；长期看它会是库里行数最多的表之一。

考虑过的退化方案是砍掉这张表、只从 ops 的 payload 里扫 blob 变更历史。否掉的理由：那样答不了「这张照片是什么时候被打上这个 tag 的」，而在归档软件里这是会被真实问到的问题。

**op 的粒度是批。** "给 500 个文件打 tag" 是**一条** op 带 500 个 target，不是 500 条。否则撤销要点 500 次。

**op 不能严格限制在单 box 内。** 有三类操作天生跨 box：① 跨 box 批量打 tag（按 tag 筛出横跨 12 个 box 的 50 个文件再批量打标，是核心工作流）；② tag 树自身的操作（全库影响，且 tag 树不属于任何 box）；③ box 创建/删除，文件在 box 间移动。

`op_boxes` 索引表解决了这个矛盾：按 box 查历史 = `JOIN op_boxes WHERE box_id = ?`，走索引，量级几千行。**性能特性拿到了，但没有牺牲"一次批量操作 = 一条 op = 一次撤销"的语义。** tag 树操作单独记 `scope='tags'`，有自己的历史视图。

**payload 不进列表查询。** 导入把 payload 从几百字节变成几 MB（5000 个文件约 1 MB JSON），而历史面板的每一行只渲染 id、时间、action、source 和「是否已被撤销」——payload 一个字节都用不到。所以：

- **列表查询选的列里没有 `payload`。** 否则 `kist log -n 20` 撞上二十条导入就要读 20 MB 来打二十行
- **只有「读一条」和「重放」读完整行**（撤销要拿 payload 算 `Inverse`）
- **`Rebuild` 用游标逐条读**，内存不随日志长度增长。用「先取全部 op 再遍历」的写法，一个十万文件的库光 payload 就是几十 MB 常驻

这条有测试守着。写成测试而不是注释，是因为给列表加字段最自然的做法就是往那个列常量里加一列，而那会静默地把这个决定撤销掉。

### 2.3 Apply 与 Inverse

每种 op 实现两个方法：

```go
type OpAction string          // 判别值，存进 ops.action

type OpHandler interface {    // 处理器，按 action 注册
    Apply(tx Tx, payload []byte) error
    Inverse(payload []byte) (OpAction, []byte, error)
    Targets(payload []byte) (Targets, error)   // 从 payload 提取索引表的行
}
```

**`Inverse` 要连 action 一起返回。** 第一版签名只返回 payload，那是不成立的——`create_box` 的反向是 `delete_box`，是另一个 action，只给 payload 的话调用方无从知道该拿哪个 handler 去 apply。

**`Targets` 是不变量 4 的落点。** `op_boxes` / `op_files` 是 payload 的索引，必须能从 payload 单向重建；把这件事做成 handler 接口的一个方法，就没有哪条写入路径能绕过它——忘了实现是编译错误，实现错了是 `Rebuild` 的测试失败。

**要让 `Inverse` 算得出来，payload 必须自带 before 状态。** 移动文件要同时记旧路径和新路径。这是写 op 定义时最容易漏的一点，也是 code review 时必须逐个检查的一点。

#### 2.3.1 `Apply` 必须是纯函数：重建的确定性

`kist rebuild` 要从 ops 重放出**完全相同**的库。这要求一条贯穿性的不变量：

> **决策在生成 op 时做完，`Apply` 只是执行。**

`Apply` 不生成 ID、不读时钟、不做任何依赖当前状态的判断——payload 里有什么就写什么。四类最容易违反的地方：

| 违反点 | 后果 | 正确做法 |
|---|---|---|
| `Apply` 里调 `uuid.New()` 生成 `File.id` | 重放生成一批全新 ID，**所有引用全断** | 由 `library` 预先生成，写进 payload |
| `Apply` 里用 `time.Now()` 写 `created_at` | 重放后整个字段变成重建那一刻，**被抹平** | 一律取 `ops.ts`（与 1.5.1 的 `updated_at` 同规则） |
| 导入重名时在 `Apply` 里算改名 | `发票.jpg` → `发票 (2).jpg` 依赖当时目录内容，重放可能得到不同名字 | **最终名字**写进 payload |
| blob 碰撞后缀 `.1` 在 `Apply` 里决定 | 同上，依赖当时磁盘状态 | 最终 key 写进 payload |

这就是事件溯源的老规矩——**命令做决策，事件记结果**。副作用是 `Apply` 极易测试（纯函数），且撤销与重放天然安全。

conformance suite 里应当有一条固定测试：**导入一批数据 → 记下全库快照 → `rebuild` → 快照必须逐字节相同。**

### 2.4 撤销与回溯

**撤销 = 追加反向 op，不是回滚。**

```
op 47: 删除 3 个文件
op 48: 撤销 op 47      ← 追加，不是抹掉 47
op 49: 撤销 op 48      ← 撤销也能被撤销
```

**历史回溯 = 从 HEAD 反向重放。**

```
当前状态 (op 500) ──Inverse(op500)──> op 499 时的状态 ──Inverse(op499)──> …
```

从 op 0 往前重放需要一个起点状态，所以才会想到要检查点；从 HEAD 往回退则**永远有现成的起点**——当前物化视图本身就是那个检查点。回溯 K 步的代价是 O(K)，与该 box 总共有多少 op 无关。

**因此不需要快照检查点这个概念。** 而且这套机器本来就要写（撤销需要 `Inverse`），反向重放就是连着调 K 次，零额外代码。

**默认回溯上限 1000 步**，性质是安全阀（防止有人输个 100000 把服务拖住），不是性能补丁。CLI 上不设限（`kist replay --deep`）。UI 必须诚实地说出边界：「只能回溯到 2026-03-14（最近 1000 次操作）」，不能静默截断。

**内容可能已被 GC。** 回溯到某时点，元数据状态能完整重建，但如果那个 blob 已过保留期被回收，内容就没了。历史视图里文件条目在，标注"内容已过保留期"，不报错。

### 2.5 隔空撤销：严格模式

在 op 500 想撤销 op 3，`Inverse(op3)` 描述的 before 状态可能早被后面的操作改掉了（它想恢复的文件已被移到别的 box，或已被删）。

**v0.1 采用严格模式：apply 前校验 before 状态是否吻合，不吻合就拒绝并说明是哪条 op 挡住了。**

理由：归档软件里，"我以为撤销成功了但其实只恢复了一半"比"撤销失败了"危险得多。尽力模式（能恢复的恢复、冲突的跳过并列清单）留到有真实需求。

**校验住在 `Apply` 里，不单开一个 `Check` 方法。** 三条理由：

① 它**不是决策而是断言**——要么原样执行，要么报错退出，不存在"根据当前状态走另一条路"。所以它不违反不变量 3，那条禁的是依赖当前状态**做出不同的行为**。

② **正向 op 走同一条路也是对的。** 正向 op 由 `library` 从当前状态生成，校验必然通过；`kist rebuild` 重放时前序 op 已经把状态放到位，校验同样通过。**校验失败只可能发生在隔空撤销上**，正是本节要拦的场景。

③ 单开 `Check` 意味着每个 handler 把 before 状态的比对写两遍，或者 `Apply` 转头去调 `Check`——那还不如直接写在 `Apply` 里。

**比对只看语义字段。** `created_at` 不可变，`updated_at` 是派生状态且按 1.5.1 ④ 不参与 `Inverse`——把它纳入比对的话，任何一次撤销都会因为"时间戳对不上"而失败。

### 2.6 模块边界

```
cmd/kist              CLI: init / serve / import / verify / scrub / gc /
                           relink / rebuild / undo / replay
internal/
  domain/             Box File Tag Blob Op Query —— 纯类型，零依赖
  store/              DAL 接口 + conformance test suite
    ├── sqlite/
    └── postgres/
  oplog/              op 定义、Apply、Inverse、版本号分配、反向重放
  blob/               内容寻址存储 + 链接农场 + 能力探测
  library/            ★ 唯一的写入口
  extract/            EXIF / 文件固有属性（可插拔）
  derive/             缩略图 / 预览 / 转码
  api/                HTTP JSON
  web/                embed 前端产物
web/                  前端源码
```

**最重要的不变量：`library` 是唯一能写的包。** 每个写操作在**一个事务里**完成三件事——生成 op、持久化 op、apply 到物化视图。`api` 和 `cmd` 只能调 `library`，不能碰 `store` 的写接口。

这条守住了，"任意操作可回退"就是结构保证的，不是靠自觉。

### 2.7 并发与多进程：一把写锁 + 一个版本号

1.6 写着一条前提假设：内存 tag 树的一致性依赖「`library` 是唯一写入口 **+ 单进程**」。只要 kist 还只是 CLI，这条自动成立。`kist serve` 一出现它就破了——人当然会在 serve 跑着的时候开个终端 `kist import`。

#### 先划掉一个不是问题的：SQLite 争用

直觉上最吓人的是「500 GB 的导入持有几小时写锁」。**不会。** 导入管线（3.7）把 blob 落盘、哈希、扫描全放在事务外，只有最后写 op 那一下进事务：

```
for 每个候选文件 { 哈希、落 blob、在内存里攒 payload }   // 几小时，不碰事务
write(ActionImportFiles, payload)                        // 一个事务，毫秒级
```

而 WAL 下读者本来就不阻塞写者。所以多进程在 SQLite 这一层是**安全且不慢的**，代价只在最后那一瞬间排队。

#### 真正会坏的是三件事

**① 内存 tag 树与计数过期。** 别的进程建了 tag、打了 tag，serve 进程不知道。后果是数字不对、新 tag 不出现——**难看，但不毁数据**。

**② `boxes/` 投影的目录名缓存过期，这条最严重。** `library` 缓存了每个 box 当前的投影目录名，3.4.1 的增量 rename 全靠它区分「改名」和「第一次投影」。CLI 改了 box 名字之后，serve 进程的缓存还记着旧名，于是 serve 的下一次增量投影会走「第一次投影」那条路——**新建一个目录，而不是把旧的改名**。`boxes/` 下同时躺着 `云南/` 和 `云南-2019/`，两份链接指向同一批文件。

不变量 1 兜住了正确性（`relink` 一跑就没了），但在有人想起来跑 `relink` 之前，这是**静默**的。比 ① 严重一个量级。

**③ 一个在事务外的读-改-写窗口。** 导入在循环开始前读一次 box 里的已用文件名，然后在内存里分配不重名的名字，最后一次性提交；而 `files(folder_id, name)` 上是 UNIQUE 索引。两个进程同时往一个 box 导入，会双双认为 `IMG_001.jpg` 是空的，第二个在**提交那一刻**撞约束。跑了三小时，最后一秒整批失败。

这是唯一一个真的需要「锁」的地方，而且**它的作用域必须比数据库事务宽**——窗口在事务外面，SQLite 自己的锁救不了它。

#### 决定 ①：`kist.lock` 上的一把进程间写锁

OS 咨询锁（Unix `flock`、Windows `LockFileEx`，两个平台文件，几十行；这个仓库已经在做同形状的事，比如 3.5 的链接能力探测）。

**作用域是「一次逻辑写操作」，不是进程生命期。**

| 持锁 | 不持锁 |
|---|---|
| `write()` 的每个调用方 | `verify` |
| 写后的增量投影 | `scrub` |
| `relink` / `rebuild` | `repair` |

**选咨询锁而不是 pidfile，决定性理由是进程崩了内核自动释放**——「过期锁」这个问题类别根本不存在，不需要判活、不需要 `--force-unlock`、不需要向用户解释什么叫僵尸锁。

**锁被占住时等 5 秒再报错。** 写操作本身是毫秒级的，绝大多数等待会在几毫秒内结束，直接失败只会制造无谓的重试。超时后的错误**必须说出占用者是谁**：锁文件里写 pid 和命令行，纯诊断用途，不参与正确性判断（正确性完全由内核的锁负责）。

**进程内还要一把普通的互斥锁。** serve 天然会并发处理请求，两个浏览器标签页同时提交就是两个并发写。Go 在 Unix 上的 `flock` 是 per-open-file-description 的，同进程二次加锁确实会阻塞——但依赖这个细节不如直接写一把 `sync.Mutex`：它更快、更明显，而且不必去查每个平台的锁语义到底是 per-process 还是 per-fd。

#### 决定 ②：读路径上比一次版本号

3.12 已经定了「op ID 就是版本号」。所以「缓存是否过期」不需要发明任何新概念：

```sql
SELECT MAX(id) FROM ops
```

主键上一次 lookup。进入任何依赖缓存的读之前比一次，与缓存建立时的值不同就重载 tag 树和目录名缓存。

**这不是失效通知，是在唯一会出错的那一刻轮询。** 没有 IPC、没有订阅、没有心跳，进程数任意。8 节里那条「多进程失效通知」的逃生舱因此依然挂在那里没被用掉——它的触发条件是官方后端上多进程共享 Postgres，那时候 `MAX(id)` 一次往返的成本才开始要紧。

#### 为什么 `verify` / `scrub` / `repair` 不持锁

因为它们跑得久，而**边跑边导入是正常需求**：`scrub` 是第一个真会跑几小时的命令，禁止在它跑着的时候干活等于没人会跑它。

不持锁是安全的，两条各自独立的理由：

- **`verify` 和 `scrub` 不写。** 它们读到的可能是一个正在变化的库，所以结论是「这一刻的快照」而不是「此后恒真」——这本来就是完整性检查的语义，3.8 的报告也是这么措辞的
- **`repair` 写 blob，但 blob 是内容寻址 + 原子写的。** 并发写同一个 key 是幂等的，写不同 key 互不相干。而它**写不出 op**——`internal/arch` 禁止 `internal/integrity` import `oplog`，这是结构保证不是约定

#### SMB / NFS

3.11 已经警告库不该放在网络文件系统上，理由是 SQLite 的锁语义在那里不可靠。**`flock` 在 NFS 上同样不可靠，结论一致，不新增限制**——但这把锁落在那条警告的覆盖范围之内，别以为躲开了 SQLite 就躲开了问题。

#### 否掉的三条路

**❌ CLI 检测到 serve 在跑就转成 HTTP 客户端。** 这是 open-questions 里的原倾向，现在推翻。三条理由：

1. **它给整个 CLI 上税，只为了修一个缓存问题。** 每个命令都要有 API 对应物才能用，`rebuild` / `verify --deep` / `repair` 这些运维命令走 HTTP 很别扭，而 `cmd` 要为每个命令维护两套代码路径
2. **它把 CLI 的发布节奏绑死在 API 的完整度上。** 一个新 CLI 命令要等它的端点先做完
3. **检测本身是脆的。** serve 在 Docker 里、库在挂载卷上、pidfile 属于另一个 namespace——判断「serve 在不在跑」比原问题还难，而判断错的后果是静默走错分支

**❌ 进程生命期的库级排他锁**（一个进程占住整个库，另一个直接退出）。最简单，但它挡不住 ②——serve 没在写的时候照样会读到过期的目录名缓存。而且它把「serve 开着就不能用 CLI」变成常态，代价远大于收益，尤其是在弄清楚 SQLite 争用根本不是问题之后。

**❌ 放弃内存树，每次查 DB。** 决定 ② 让它没必要了。1.6 那套简化（移动子树 O(1)、不要物化路径列、计数在树上向上汇总）是拿内存树换来的，为一个用一次主键 lookup 就能解决的问题把它退掉不划算。

## 3. 存储层

### 3.1 磁盘布局

```
~/kist/                          # kist init 时指定
├── DO-NOT-EDIT.txt
├── kist.db                      # 权威元数据
├── kist.toml                    # 配置
├── kist.lock                    # 写锁（OS 咨询锁，见 2.7）；内容纯诊断
├── blobs/                       # 权威内容，不可变
│   ├── tmp/                     # 写入暂存区
│   └── sha256/ab/cd/abcdef01…   # 算法前缀 + 两级分片，0444
├── boxes/                       # ★ 投影，可整棵重建
│   ├── 2019-08-12_办护照/
│   │   └── 护照.jpg
│   └── 2026-03_体检/
│       ├── 检查报告.pdf
│       └── 发票/门诊发票.jpg
└── derived/                     # 派生媒体，可再生但视为热层
    └── sha256/ab/cd/<hash>/
        ├── thumb_512_v1.webp
        ├── preview_2048_v1.webp
        └── preview_1080p_v1.mp4
```

**权威的只有 `kist.db` 和 `blobs/`。** `boxes/` 和 `derived/` 都是推论，`kist.lock` 里的内容（持锁者的 pid 和命令行）纯粹是给人看的错误信息，删掉它不损失任何东西——正确性完全由内核持有的那把锁负责。

**库位置由 `kist init` 的交互流程确定**，形态参考 `ssh-keygen` / `aws configure`：逐项提问、每项都有默认值、一路回车即可完成，默认落在 `~/kist`。

不设"静默默认值"是因为几百 GB 的归档躺在系统盘上是个真实的坑，而不设默认值又会让新用户第一步就卡住。交互流程两头都躲开了：默认值照给，但**创建前把探测结果摊开**——目标路径、可用空间、链接方式（reflink / hardlink / symlink / 完整拷贝，见 3.5）、`blobs/` 与 `boxes/` 是否同一文件系统——让用户在看得见后果的情况下按回车。

平台惯例目录（`~/Library/Application Support/kist`、`$XDG_DATA_HOME`）考虑过，否掉：它们的设计前提是"应用数据不该被用户翻到"，而 kist 的库恰恰是用户**想**翻到的东西——3.11 的备份方案就是让人对着库目录 `rsync`。

非交互场景（脚本、CI、测试）走 `kist init <path> --yes`，不读 stdin。**交互与非交互必须是同一条代码路径的两种输入源**，否则测试覆盖不到用户真正走的那条。

### 3.2 外部改动：不对账，只重建

用户在 Finder 里删了、改名了、拖乱了 `boxes/` 里的东西——**不需要任何对账逻辑，运行一次 `kist relink` 整棵重建即可**，因为数据从来没在那儿，一直在 `blobs/` 里。

这一条砍掉了原本设计里最贵的一块：fsnotify 监听、双向合并、把外部改动翻译成 op。那套东西不光工作量大，语义还根本讲不清楚（用户在 Finder 里把 `报告.pdf` 拖到另一个文件夹，在 op log 里到底算什么意图？）。

同时"kist 死了数据还在"这条也保住了——`boxes/` 树还在磁盘上，人可读。

**剩下要守的只有 `kist.db` 和 `blobs/`：** 放进不常浏览的位置、blob 一律 0444 且文件名是哈希（用户翻到了也不知道那是啥）、`DO-NOT-EDIT.txt` 说明。

但**有一类"外部改动"永远消不掉**——磁盘坏道、备份只恢复了一半、同步客户端搅乱硬链接、杀毒软件隔离文件、写到一半断电。这些不是用户不听话，是物理现实。所以仍然需要 `kist verify`（见 3.8）。

### 3.3 blob 层

**哈希用 SHA-256。** 不是因为最快（BLAKE3 快 3-5 倍），而是因为**用户能在命令行上自己验**（`shasum -a 256`）——归档软件的信任来自可独立验证。且现代 CPU 有硬件加速（~2GB/s），瓶颈在磁盘不在 CPU。

**表结构：**

```sql
blobs (
  key     TEXT PRIMARY KEY,   -- "sha256:abcd…" 碰撞时 "sha256:abcd….1"  ← 唯一
  sha256  TEXT NOT NULL,      -- "abcd…" 裸值                          ← 非唯一索引
  size    INTEGER NOT NULL
)
```

`key` / `sha256` **必须分开两列**，因为碰撞后缀让这两个值的唯一性不同：`key` 是地址（`files` 外键指它，磁盘路径由它推导，全局唯一）；`sha256` 是内容指纹（去重时 `WHERE sha256 = ?`，碰撞时会返回多行，所以不能是唯一索引）。

**算法前缀必须同时出现在 key 值和磁盘路径里。** 只在路径里加而 DB 存裸 hex 是不够的——从 DB 拿到哈希值时没法知道该去哪个算法目录找。将来换 BLAKE3 或 SHA-256 出问题时，新旧可共存、按需迁移。

顺带一个免费的护栏：`:` 在 Windows 文件名里非法，所以 `sha256:abcd…` **不可能被误当成路径使用**——想拼路径的代码会当场炸掉，而不是悄悄写出坏文件。

**key 不存成路径形式**（如 `sha256/ab/cd/xxx`），四个理由：① 会把 DB 和某一种磁盘布局焊死，改分片深度要重写全库；② 远端存储（S3 / rclone）布局不同，而 key 是全局身份；③ `ab/cd` 是哈希前缀的冗余抄写，多一个真相来源；④ 时间戳后缀不可重算且本身可能撞，而计数器几乎免费（检测碰撞时已经在事务里查过 `sha256` 了）。

**原子写：** 流式读入 → 边写 `blobs/tmp/<rand>` 边算哈希（单次遍历）→ fsync → 决定是否保留 → `chmod 0444` → rename 到最终位置 → fsync 父目录。rename 在同一文件系统内是原子的。

**`chmod 0444` 放在"决定保留"之后**，而不是 fsync 紧后面。去重命中时要删掉临时文件，而在 Windows 上删只读文件必须先清掉只读属性——把 chmod 推迟到确定要保留时，丢弃路径上的临时文件始终是可写的，省掉一整条平台分支。对崩溃安全没有影响：内容的持久化由 fsync 保证，与权限位无关。

**去重命中时的三分支：**

```
算出 sha256:abcd…
  ├─ 目标不存在  → 直接写入
  └─ 目标已存在 → 单次遍历读已存在的 blob，同时做两件事：
                    ① 喂哈希器 → 与文件名比对
                    ② 与临时文件逐块字节比对
       ├─ 哈希与文件名不符   → 已存在的 blob 损坏
       │                      → 用刚验证过的新文件修复，高声告警
       ├─ 哈希相符且字节相同 → 去重命中，丢弃临时文件
       └─ 哈希相符但字节不同 → ★ 真碰撞
                              → 新 blob 存为 sha256:abcd….1
                              → 严重告警（几乎必然意味着 bug 或硬件故障）
```

**两个检查缺一不可，因为它们回答的是不同的问题。** 这里推翻了本节的第一版：那版只做重新哈希，理由是"与字节比对成本相同但诊断更清晰"。**那个方案检测不出真碰撞**——如果已存在的 blob 重哈希后与文件名一致、新文件也哈希成同一个值，这恰好就是碰撞的定义，重哈希在"内容相同"和"真碰撞"两种情况下给出完全相同的结果。于是第三个分支永远不会被触发，而它正是本节存在的理由。

分工是：**重新哈希查"已存在的 blob 有没有烂"，字节比对查"是不是碰撞"。**

**合成一次遍历，所以成本没有增加**：读已存在的文件时每块既喂哈希器又与临时文件对应块比对。临时文件本来就在磁盘上、刚写完还在页缓存里。重哈希原本主张的两个好处也都保住了——损坏时能用刚验证过的新文件自愈，且复用同一个哈希器。

**为什么必须处理碰撞而不是忽略它。** SHA-256 意外碰撞确实不是现实威胁，但 git 在这件事上栽过跟头：SHA-1 被 SHAttered 攻破后，人们发现 git 的碰撞行为是**静默保留旧对象、丢弃新对象**，是实打实的数据丢失 bug，补救花了多年。而认真对待的系统有先例：ZFS 去重有 `verify` 选项做完整比对，btrfs 去重永远做字节比对。加上 `.1` 后缀分支后，这不再是"一个我们选择忽略的风险"，而是"一个已处理的分支"——代价只有几行代码，因为完整比对本来就要做。

**不提供 `--trust-existing` 之类的加速开关。** 它会连碰撞检测一起跳过，是个藏在性能选项背后的安全陷阱。默认行为就是唯一行为。

### 3.4 boxes/ 投影层：跨平台差异在这里消化

box 目录名：`<yyyy-mm-dd>_<slug>`，日期取 `start_at ?? created_at`，**长度反映精度**：

```
boxes/
├── 2019_童年老照片/            ← year
├── 2019-08_办护照/             ← month
├── 2019-08-12_婚礼/            ← day
└── 2019-08-12_1430_午餐/       ← minute
```

**分钟精度用 `_hhmm` 而不是 ISO-8601 的 `T14:30`**，因为 **`:` 在 Windows 文件名里是非法字符**——`2019-08-12T14:30_午餐` 在 Windows 上根本创建不出来。

这又是本节那条原则的一次应用：**DB 存规范值，投影层消化平台差异。**

| 精度 | DB 里存 | 目录名 |
|---|---|---|
| year | `2019` | `2019_slug` |
| month | `2019-08` | `2019-08_slug` |
| day | `2019-08-12` | `2019-08-12_slug` |
| minute | `2019-08-12T14:30` | `2019-08-12_1430_slug` |

DB 里必须保留 ISO-8601（含 `T` 和 `:`），因为**那个格式的字典序就是时间序**——1.3 的整套变精度日期方案建立在这个性质上，不能为了目录名去动它。

**为什么用 `start_at` 而不是 `created_at`。** 你 2026 年导入 2019 年的照片，用 `created_at` 会让十年人生历史全部挤在导入的那几天里——而人可读浏览是 `boxes/` 存在的唯一理由。"目录名稳定"这个理由在这里不成立：`boxes/` 是投影，改名零成本。`created_at` 作为兜底，所以每个 box 一定有日期。

变长前缀有个小瑕疵：同一年内，只有年份精度的 box 会排在有月份的后面（`-` 的 ASCII 小于 `_`）。可接受——补零成 `2019-01-01_童年老照片` 会让浏览者以为那是 1 月 1 日发生的事，是更大的问题。

**文件名本身不合法时（尾随点、首尾空格）是 per-file 失败，不自动修。** 自动 trim 会让用户的文件被静默改名，而他们永远不会知道自己的文件其实不叫那个名字——对一份要在十年后还看得懂的归档，这比让他们改完再导一次糟得多。报错里要说清楚该怎么办。

**跨平台差异全部在投影时处理，DB 里存干净的真名：**

| 问题 | 处理 |
|---|---|
| Windows 非法字符 `<>:"/\|?*`、保留名 `CON` `PRN` `NUL` `COM1`、结尾的点和空格 | 投影时替换为全角或 `_`。**所有平台用同一套规则**，见下 |
| Windows `MAX_PATH` 260 | Go 里用 `\\?\` 前缀绕过；同时限制 box 名和层级深度 |
| macOS 规范化成 NFD，Linux 存原始字节 | **DB 里一律存 NFC**，verify 时两边都 NFC 化再比。中文名尤其容易踩 |
| 两个 box 同名 | slug 冲突时追加短 id 后缀 |
| 同目录同名文件 | DB 层唯一约束，导入时自动改名——但**先比 `blob_key`**，同名同内容是跳过而不是改名（见 3.7.1 ②）|

**净化规则在所有平台上一视同仁。** 最初写的是「同一个库在 Mac 上创建、拷到 Windows 打开，投影名不同但 DB 一致」，即净化平台相关。改掉了，三条理由：

1. **`relink` 必须幂等，跨平台也得幂等。** 平台相关的话，把库目录从 Mac 挪到 Windows 再 `relink`，整棵树会被重命名一遍——而投影的每一次大改名都是一次 Windows sharing violation 的机会（见 3.4.1 的已知失败模式）
2. **CI 能真正测到 Windows 的规则。** 净化统一之后，Linux 上跑的测试就是 Windows 上跑的测试；平台相关的话，`CON`、尾随点、`<>:"/\|?*` 这些规则只有 windows runner 会执行到，而那正是最容易写错的一段
3. **代价只是审美。** 被替换的是 `<>:"/\|?*` 和控制字符——`/` 在 POSIX 上本来也非法，`:` 在 macOS 的 Finder 里会显示成 `/`，剩下的在文件名里本来就少见

**`Sanitize` 必须幂等**，理由同第 1 条：`relink` 会把它跑遍全库，不幂等就意味着每跑一次全库改名一次。这一条有专门的测试盯着。

#### 3.4.1 投影的增量维护

`boxes/` 可以整棵重建，但平时要跟着 DB 增量变。核心规则只有一条：

> **一律优先 `os.Rename`，不要 unlink + 重建链接。**

改目录名是**元数据操作，O(1)**，与目录内有多少文件无关。里面的硬链接和 reflink 完全不受影响——它们是指向 inode 的目录项，重命名父目录只动父目录自己那一条目录项，不碰任何子项。而 unlink + 重建对一个装了两万张照片的目录是灾难。

| 触发 | 投影动作 |
|---|---|
| box 改名 / 改 `start_at` | `os.Rename` box 目录（`start_at` 变了目录名就变，见 3.4） |
| folder 改名 / 移动 | `os.Rename` 子目录 |
| file 改名 / 移动 | `os.Rename` 链接 |
| 导入 / 删除 | 建 / 删链接 |
| rename 后 | 重新 `os.Chtimes` 应用 `updated_at`，**只对目录**（见 1.5.1 和下面那条）|

**顺序沿用 3.7：DB 事务先提交，再动投影。** 投影失败**永远不是数据丢失**——记日志、置投影脏标记、`kist relink` 修好。与导入管线"第 5 步失败 → relink 补上"是同一条规则。脏标记要在 UI 上可见，否则投影会静默过期直到有人跑 `verify`。

**文件链接一律不设 mtime，只有目录设。** 1.5.1 说的就是"目录的 mtime"，这里把理由补上，因为它不显然：

`hardlink` 模式下**链接和 blob 是同一个 inode**，给链接设 mtime 就是在改 blob 文件的 mtime。更糟的是去重——两个 file 行指向同一个 blob 时它们的 `updated_at` 不同，投影会来回改写同一个 inode，**每次 `relink` 的结果都可能不一样**，而 `relink` 必须是幂等的（它是所有投影问题的兜底修复手段，一个每跑一次都在改东西的修复手段没法当兜底用）。

目录没有这个共享问题：一个投影目录只对应一个 folder 行。

**「这是一次改名」这个判断来自一个进程内缓存。** `library` 记着每个 box 当前的投影目录名，增量维护全靠它区分「改名」（`os.Rename`，O(1)）和「第一次投影」（建目录）。缓存过期的后果不是报错而是**静默多出一个目录**——旧名下的链接还在，新名下又建了一套，两份指向同一批文件。

单进程下这条由「写完就更新缓存」保证。多进程下它会真的发生，是 2.7 里最严重的那个失效，也是那一节存在的主要理由。

**已知失败模式：**

- **Windows sharing violation** ⚠️ 平台特有且常见：只要有任何进程持有目录内某个文件的句柄，**重命名父目录就会失败**。用户正在预览一张图、杀毒软件正在扫描，都会触发。Linux / macOS 没有这个问题
- 目标名已存在（见下）、权限不足

**重名后缀会传染。** 3.4 定了"slug 冲突时追加短 id 后缀"，但一个 box 改日期，可能让它跟另一个 box 撞名，**也可能让原本的冲突消失**——box A 的改动会导致 box B 的目录名需要变。

解法是让投影名成为 DB 状态的**纯函数**：冲突时按 `id`（UUIDv7，即创建顺序）排序，第一个用裸名，其余追加短 id。给定全库状态，每个目录名唯一确定。

而**增量 rename 本质上是优化，`relink` 才是正确性兜底**。规则：试着增量 rename；一旦情况复杂（撞名连锁、rename 失败），直接退回 relink。反正它只建链接不拷数据。

### 3.5 链接能力探测与降级

| 平台 / 文件系统 | 硬链接 | reflink |
|---|---|---|
| macOS APFS | ✅ 文件（目录不行） | ✅ `clonefile(2)` |
| Windows NTFS | ✅ 不需要管理员权限，单文件上限 1024 | ❌ |
| Linux ext4 | ✅ | ❌ |
| Linux btrfs / XFS | ✅ | ✅ `FICLONE` |
| exFAT / FAT32 | ❌ | ❌ |
| SMB / NFS | ⚠️ 不可靠 | ❌ |

`kist init` 时在库目录做一次**真实探测**（不靠猜文件系统类型），结果记进配置，启动时复验：

```
reflink → hardlink → symlink（非 Windows）→ 完整拷贝
```

同时用 `stat` 比对 `blobs/` 和 `boxes/` 的 `st_dev`——**不在同一文件系统就直接降级到拷贝**。

**Windows 上只用硬链接不用符号链接**：符号链接需要管理员权限或开发者模式，硬链接不需要。

**macOS 上优先 reflink**：硬链接共享 inode，用户就地编辑 `boxes/` 下的文件会直接改坏 blob 并影响所有引用；reflink 是独立 inode、共享块，没有这个问题。（blob 的 0444 会让就地编辑失败，这是第二道防线。）

探测结果必须在 UI 上如实显示：「当前存储不支持去重，`boxes/` 会占用额外 N GB」。

**注意：** rsync 要加 `-H` 才保留硬链接；Dropbox / iCloud 这类同步客户端不懂硬链接，会把每个链接当独立文件上传，吃掉全部去重收益。

### 3.6 derived/：不是 cache

叫 `derived/` 而不是 `cache/` 是有意的——**将来做分层存储时，派生文件恰恰是应该留在本地热层的那一层**。原图搬去 S3，缩略图和预览留本地，浏览才依然秒开。当成"随时可删的缓存"就把这个故事讲反了。

- **不进 `blobs/`**：派生物进 blob 池会污染引用计数，且用户 `rsync blobs/` 时期待的是"我的真实数据"，不该被转码文件撑大
- **文件名带 recipe 版本 `_v1`**：改了编码参数就用 `_v2` 懒生成，旧的过期即可，不用全库重跑
- **生成时机分级**：缩略图导入时同步生成（网格必需，几十毫秒）；大预览和视频转码**懒生成 + 队列**（4K 视频转码是分钟级 + 高 CPU，绝不能挂在导入路径上）
- **EXIF orientation 必须在生成缩略图时应用**（最经典的横竖颠倒 bug）
- **记录 `generation_ms`**：备份策略就是一句 `generation_ms > 阈值`——图片缩略图自然落在阈值下（全库几分钟就能重建），视频转码自然落在阈值上（约 1 倍实时，几百个视频就是好几小时 CPU）。用户不需要理解和配置这件事

### 3.7 导入管线：崩溃安全由顺序保证

**前置约束：box 必须已存在。导入不推导任何 box 信息，不自动建 box。**

**默认跳过点开头的文件和目录，`--hidden` 打开。** `.DS_Store`、`Thumbs.db`、`desktop.ini` 是操作系统的排泄物不是归档材料，一个每个目录都默默攒一个的归档库比一个要你多打一个 flag 的更糟。

**空目录不产生 folder 行。** folder 是懒创建的——只有真的有文件落进去时才建。这让 payload 只包含实际用到的目录，撤销时「目录必须是空的」那条断言也不会被一堆空壳绊住。

```
1. 流式写 blobs/tmp + 算哈希
2. fsync → 0444 → rename 到 blobs/sha256/ab/cd/<hash>
3. 提取 EXIF / 文件固有属性 → `metadata`（**M3**，M1c 里这一步是空操作）
4. ── 事务 ── 插 op + 插 files 行 + 插 metadata 行 ── 提交 ──
5. 在 boxes/ 下建链接
6. 生成缩略图（异步）
```

| 崩在哪 | 后果 | 谁来收拾 |
|---|---|---|
| 1–2 | 孤儿 blob（只占空间，不危险） | `kist gc`（v0.1 无，暂时堆积） |
| 3 | 无（派生数据） | 重跑 |
| 4 | 孤儿 blob（同上） | `kist gc`（v0.1 无，暂时堆积） |
| 5 | 缺链接 | `kist relink` |
| 6 | 缺缩略图 | 按需再生 |

**关键在于 blob 先于 DB 落盘。** 反过来的话，DB 会指向一个不存在的 blob——那才是真正的数据损坏。

#### 3.7.1 中断、部分失败与幂等

**① `Ctrl-C` 是优雅停止，已完成的部分提交成一条 op。**

第一次 SIGINT：停止接收新文件，把已经走完第 4 步的文件提交成**一条** op，打印「已导入 N 个，剩余 M 个未处理」，以非零码退出。第二次 SIGINT：立即退出，当前事务回滚。

**被打断的那一个文件不算失败，算「没看过」。** 中断到达时正在读的文件会拿到一个 `context canceled`，但用户按的是 Ctrl-C——把它列进「failed」既是噪音，也让「我停下了」和「我的文件有问题」变得分不清。它计入「未处理」。

退出码同理分两种：有文件真的失败是一回事（`some files were not imported`），被用户停下是另一回事（`stopped before finishing`）。两者都非零——停下终究不是做完——但不能是同一句话。

否掉的两条：

- **❌ 整批回滚。** 语义最干净，与其他批量操作完全一致。但 500 GB 的导入跑到 99% 被打断就全部白做，而且整个过程要持有一个长事务——在 SQLite 上那意味着几小时的写锁
- **❌ 每 N 个文件提交一条 op。** 恢复友好，但直接推翻 2.2 定下的「一次导入 = 一条 op = 一次撤销」。撤销一次导入会变成撤销一串 op，回收站和历史面板全都要跟着改

选优雅停止的关键在于**它不需要为中断额外付任何代价**：3.9 已经定了 v0.1 不做 GC、孤儿 blob 只占空间不危险，所以中断时那些已落盘、未被任何 op 引用的 blob 本来就在既定设计内。

**② 导入是幂等的：同 folder、同 name、同 `blob_key` → 跳过。**

1.5 定了「导入时冲突自动改名 `发票 (2).jpg`」。但那条规则单独存在时，中断后重跑同一个目录，会让**每一个已经导进去的文件都多出一个 `(2)` 副本**——这正是①最直接的用户可见后果。所以自动改名之前先比一次 `blob_key`：

| folder + name | blob_key | 动作 |
|---|---|---|
| 不存在 | — | 正常导入 |
| 已存在 | **相同** | **跳过**，计入「已存在」 |
| 已存在 | 不同 | 自动改名 `发票 (2).jpg` |

代价接近零（`files(folder_id, name)` 那条唯一索引本来就在，只是多读一列），换来的是「重跑同一个目录永远收敛到同一个结果」。它也不损失任何能力：「同一目录里放两份一模一样的文件」本来就被 `UNIQUE(folder_id, name)` 挡死了。

**③ 单个文件失败不中断整批。** 导入返回 per-file 结果（导入 / 跳过 / 失败 + 原因），结束时汇总打印，有失败则退出码非零。

这一条与「op 是原子事务，批量操作全有全无」是**故意的不一致**——5000 个文件里有一个读不出来，不该让另外 4999 个白做。边界是清楚的：**失败的文件根本不进 op 的 payload**，所以 op 本身依然原子，它记录的是「实际导入成功的那些文件」，重放必然得到同样的结果。

批量入口是 CLI：`kist import --box <box-id> ~/Pictures/2019云南/`。Web UI 里是拖拽到某个 box 上传。两条路都不需要监听目录，`inbox/` 不进 v0.1。

**保留一个用户主动触发的按钮**：box 详情页上「根据本 box 内文件的拍摄时间设置时间范围」，取 EXIF 拍摄时间的 min/max。这是用户发起的，不是导入的副作用。

（将来的"手机相册自动导入"是两步：先分析出候选 box 让用户确认创建，再导入。这个约束正好使它成为自然产物。）

### 3.8 完整性：verify / scrub / repair

三个命令，按「读还是写」「快还是慢」切开：

| | 做什么 | 代价 | 写不写 |
|---|---|---|---|
| `kist verify` | 走一遍 DB，报告不一致 | 只 `stat`，不读内容 | 只报告 |
| `kist verify --deep` | 把日志重放到一份临时副本，与当前视图逐表比对 | 一次全量重放 | 只报告 |
| `kist scrub` | 全库重新哈希，检测位翻转和坏道。可挂 cron | 读完每个字节 | 只报告 |
| `kist repair` | 从远端副本取回坏掉或丢失的 blob | 按需读远端 | **写 `blobs/`** |

**`repair` 是独立命令，不是 `scrub --repair`。** scrub 是可挂 cron 的慢操作，repair 是要人看着的写操作——合成一个开关，等于让 cron 在无人值守时覆盖 `blobs/`。因此 repair 照 3.9 给 gc 定的形态：**默认 dry-run，`--yes` 才真写**。

#### verify 查四类东西

| 类 | 查什么 | 怎么查 |
|---|---|---|
| **blob** | `blobs` 表每一行在 `blobs/` 下有没有对应文件、大小对不对 | `stat` |
| **投影** | `boxes/` 下该有的有没有、不该有的在不在、链接指向对不对 | 复用 `projection.Plan` + 一次 dry-run 的 diff |
| **结构** | 孤儿 file（folder 不在）、`file.box_id` 与所属 folder 的 box 不一致、folder 成环或跨 box、`blob_key` 不在 `blobs` 表里 | 几条 SQL |
| **孤儿 blob** | `blobs/` 下有文件但 `blobs` 表里没有 | 扫目录 |

**结构那一类是后加的**，3.8 原本只列了 blob 和链接。加它的理由：**它恰好是四条不变量被破坏时的可观测面**，而且 M1c 之后 `files` / `folders` 的写路径复杂了不少。它是 `--deep` 的廉价近似——`--deep` 能查出的它查不全，但它不用重放。

folder 的两种坏法（父目录没了、成环）**是一条查询**：从每个 box 的根往下求可达集，不在里面的就有问题。写两条的代价不是多写一遍，是两条查询要对「什么是健康的树」保持一致，而它们迟早不一致。

顺带一条实现时才想清楚的事，值得记下来因为它反直觉：**环按构造就不可能从根出发到达**。`parent_id` 是单值的，所以环里的 folder 的父亲也在环里，它就不可能同时是某个根的孩子。这才是「从根往下走」能发现环却永远不会走进环的原因——不需要环检测，也不会转不出来。

**孤儿 blob 只报告不删。** 它是「blob 写完但事务未提交」的残留（3.9），而 v0.1 不回收任何东西。让 verify 变成一个会删数据的命令，等于偷偷实现了半个 gc。

**投影检查复用 relink 的代码，不另写检查器。** `Relink` 已经是「按 `Plan` 算出期望树，与磁盘 diff，然后动手」，verify 要的就是这个 diff 的前半段。另写一个的代价不是多写一遍代码，是**两套代码迟早对同一个目录给出不同结论**，而那时你不知道该信谁。做法是给 `projection.Syncer` 加一个 dry-run 模式：算出要创建和要删除的清单，不动手。

**链接指向对不对，按 link mode 分级：**

| mode | 能不能免费确认指向正确 |
|---|---|
| hardlink | **能。** `os.SameFile(链接, blob)`——它们本来就是同一个 inode |
| symlink | **能。** 读一次 link target |
| reflink / copy | **不能。** 只能查存在和大小，内容归 scrub |

这不是遗憾，是分工。verify 的承诺是「只 stat 不读内容」；一旦为了 copy 模式去哈希，它就变成了 scrub。

#### `verify --deep`：把不变量 1 交到用户手里

不变量 1 说「`kist.db` 里除 `ops` 外每张表都可重建」。到 M1c 为止，这条只在**测试**里被验证过（`TestRebuildReproducesTheLibraryExactly`）。`--deep` 把同一个断言变成用户能跑的命令：

```
VACUUM INTO 一份临时副本  →  在副本上 Rebuild  →  ATTACH，逐表 EXCEPT 双向比  →  报告差异行
```

- **在副本上重放而不是原地**，因为「verify 不写库」这条不为它破例
- **用 `EXCEPT` 而不是比对 `store.Snapshot` 的字符串**，因为快照会把整个库拉进内存——十万文件就是几十兆。比对交给 SQL，只有差异行回到 Go 里

否掉的一条：**把 `--deep` 做成默认行为。** 但**实现时量出来的数字推翻了原本的理由**，见下。

#### 实测（M2a 收尾，4000 个文件 / 156 MB / 502 条 op，macOS + NVMe）

| | 耗时 |
|---|---|
| `kist verify` | **0.15 s** |
| `kist verify --deep` | **0.38 s** |
| `kist scrub` | **0.17 s** |

写计划时给 `--deep` 不做默认的理由是「全量重放在几十万条 op 上是分钟级的」。**这条在这个规模上完全不成立**，而且量出来才发现原因：`--deep` 的成本几乎与 op 数无关——往库里灌了 500 条 tag op 之后，它还是 0.38 s。重放本身很便宜，真正的固定开销是 `VACUUM INTO` 加十一条 `EXCEPT`。

所以理由换成实测支持得住的那条：**`--deep` 每跑一次就要把整个数据库原样写一份到磁盘上。** verify 承诺不写库，而 `--deep` 会在库旁边写一个和 `kist.db` 一样大的文件。挂在 cron 上每小时跑一次，就是每小时一次毫无意义的全库写入——对一个承诺「数据比软件活得久」的项目，这是拿 SSD 寿命换一个每次都得到相同答案的检查。

`scrub` 同理：在这个规模上它和 verify 一样快，因为 156 MB 在 NVMe 上就是眨眼的事。它的成本是**读带宽**，不是别的——实测约 900 MB/s（页缓存热），换成 500 GB 挂在 USB 的移动硬盘上就是几个小时。「scrub 慢」这句话在这个测试库上看不出来，但它在真实归档上是对的。

> **这三个数字要在库规模上一个数量级之后重测。** 十一条 `EXCEPT` 是随行数增长的，`Plan` 的排序也是；4000 个文件证明不了 40 万个文件。

#### 发现损坏之后能做什么

按价值排序：

1. **精确告诉用户哪些文件坏了。** "你 2019 年的护照扫描件已损坏"在 2026 年知道，和在 2031 年需要用时才发现，是完全不同的两件事——前者你还有机会去翻旧手机、旧硬盘、聊天记录
2. **从任意远端副本自动修复。** 这是真答案，而**内容寻址让它几乎免费**：你知道 blob 的哈希，向任何配置过的远端要这个哈希，验一遍，覆盖回去
3. **降级到 derived 层。** 原图烂了但 2048px 预览还在——画质丢了，回忆没丢。必须**明确告知**而不是静默替换
4. （v0.2+）par2 奇偶校验，给单副本用户兜底
5. 文档里建议用户把库放在 ZFS / btrfs 上（自带校验和 + 冗余可自愈）

#### 修复不写 op

repair 会覆盖 `blobs/` 下的文件，而 `blobs/` 是权威数据的一半（不变量 1）。那它要不要留一条 op？

**不留，只写日志。** 三个理由：

- 覆盖回去的是**按哈希取、验过的正确内容**。库的状态没有变，变的是磁盘从坏回到对——没有状态变更可记
- `Apply` 是纯函数，**碰不到 `blobs/`**（不变量 3）。这条 op 无处安放：重放它必须什么都不做
- 一条重放时什么都不做的 op，会让 `verify --deep` 和 `rebuild` 都多一个特例，换来的只是「日志里能看到修过」——而那本来就该在日志里，不该在 op log 里

同一条推理适用于 `blobs/tmp/` 的清理和将来的 gc：**只有改变库内容的操作进 op log。**

#### 远端不是第二个类型

**因此远端 BlobStore 在 v0.1 就是一等接口，不是 v0.2 的附加功能**——scrub 没有修复能力的话，它是个让人沮丧的功能。

但 3.10 原本那句「是 `BlobStore` 接口的第二个实现，几十行」高估了它：**远端根本不是第二个类型，就是同一个 `blob.Dir` 指向别处。** 修复只用到 `Get` / `Stat` / `LocalPath`，`Dir` 全都有。真正要加的只有一个**只读构造函数**——现在的 `NewDir` 会 `MkdirAll(root/tmp)`，而挂载成只读的移动硬盘上这一步直接失败，偏偏修复源最该是只读的。

**kist 不往远端写。** 备份是 `rsync`（3.11），远端对 kist 而言只是一个「按哈希取内容」的地方。这也是为什么它不需要第二个实现：写入侧的全部复杂度（原子写、去重、碰撞分支）都用不上。

配置形态：

```toml
[[remote]]
name = "外置硬盘"
path = "/Volumes/Archive/kist/blobs"
```

**没有 `kist remote add`。** `kist.toml` 头上就写着「手改会在下次运行时被读回去」，而加一个远端是一辈子一次的操作。有的是 `kist remote list`，它存在的理由是**让路径打错的那天是今天**，而不是数据坏掉的那天。

#### 修复的原语不是 `Put`

3.8 原本把修复写成「向远端要这个哈希，验一遍，覆盖回去」，听起来就是 `Put`。实现时发现不是，两处不同都要紧：

- **`Put` 靠哈希决定放哪，并且会走碰撞后缀**（3.3）。`Restore` 是**被告知**放哪：`sha256:ab….1` 是一个具体的槽，`Put` 会心安理得地落进 0 号，那是另一个 blob
- **`Put` 信任调用方**，因为它的调用方是在读用户自己的盘。`Restore` 不信任——它在读远端

所以有一个独立的 `Dir.Restore(ctx, r, want Key)`：边读边哈希，对不上就把暂存文件扔掉，**并且不动原来那个坏 blob**。坏内容有时候是唯一的内容。

这条验证不是形式主义，它正是**远端可以是一块无人值守的移动硬盘或一个网络共享**的原因。

#### `repair` 的 dry-run 不下载

3.9 给 gc 定 dry-run 时说的是「显示将永久删除 N 个文件」——那是纯读，没有取舍。repair 的 dry-run 有：要不要为了「确认真的能修」把每个文件都从远端拉下来验一遍？

**不要。** 那样 dry-run 就和真修一样慢一样贵，用户会直接跳过它去 `--yes`，等于没有 dry-run。它的承诺是「远端在这个 key 下有内容，大小对」——**「我看了一眼」，不是「我保证」**。

#### 报告说文件名，不说哈希

三个命令的输出统一成这个形状：

```
error: content is missing from blobs/ (1)
    云南/IMG_2.jpg — sha256:94bacd25dc9b…
    fix: kist repair
```

3.8 把「精确告诉用户哪些文件坏了」排在 verify 价值的第一位，而 `sha256:94bacd25…` 不是「你 2019 年的护照扫描件已损坏」那句话。文件名在前、摘要截短在后：摘要要等你决定去做点什么之后才有用。一批坏 blob 走**一条** `IN` 查询——损坏平时很罕见，但半恢复的备份会让它变成普遍情况，而那恰恰是报告最不能花一分钟才印出来的时刻。

完整的文件夹路径**故意不查**：那要对每个文件递归上溯一次，而 box 名加文件名已经足够认出是什么。

#### 退出码

| | |
|---|---|
| 0 | 干净，或只有 info 级发现 |
| 1 | 警告：`boxes/` 漂了，`relink` 能修；或者 scrub 没跑完；或者 repair 的 dry-run 发现了东西 |
| 2 | 错误：内容或数据库不对 |

分成两档非零而不是一档，因为这是要挂 cron 的命令，而**「你的镜像旧了」和「你的护照扫描件没了」不是同一个夜晚**。

#### 一趟没跑完的 scrub 必须说出来

`scrub` 被 Ctrl-C 之后照样交出已经查完的部分（和导入同一条规矩，3.7.1），但报告里必须有一条 warning 级的「the scrub did not finish」。

**「没发现问题」和「没查完所以没发现问题」是两句完全不同的话**，而这个命令的全部价值就是让人敢相信前一句。

### 3.9 GC 与保留期（设计就位，实现推迟到很后面的版本）

> **v0.1 不实现 GC。** 不做 GC 意味着什么都不会被销毁——在早期版本这是优点不是缺点。本节是设计留档，实现时机见第 8 节。
>
> 连带结论：**v0.1 的保留期 = 永久**，2.4 里"内容已过保留期、显示占位"的降级路径在 v0.1 根本不会发生，撤销永远能拿到内容。
>
> **推迟是零成本且可逆的**：GC 需要的引用信息全在 `ops`（永不删）和 `files` 里，两者本来就在，将来加 GC 不需要任何 schema 改动。
>
> **但有两样不能跟着推**：① `blobs/tmp/` 的崩溃残留要清；② 孤儿 blob（写了但事务未提交）会堆积，但那只占空间、不危险——`kist verify` 报告它们，不删（3.8）。
>
> **`tmp/` 清理的阈值和时机（M2a 定）**：删掉 **24 小时**以前的临时文件，跑在 `verify` 和 `import` 开头。
>
> - **24 小时和 gc 的宽限期是同一个数、同一个理由**：挡住「blob 写完但事务尚未提交」的竞态。一次导入跑不到 24 小时的话，这个数还有大量余量
> - **不跑在 `Open` 里。** `kist ls` 不该有写副作用——一个只读命令删文件，是那种平时看不见、出问题时没人想得到的行为
> - 它**不写 op**，理由同 3.8「修复不写 op」：`tmp/` 下的东西从来就不是库的内容
>
> **残余风险**：早期试用时导入 500 GB 发现搞错了、删掉，空间要不回来。缓解办法是那个阶段直接删掉整个库重来。

blob 可回收的条件是**两个引用来源都没有它**：

1. 当前 `files` 表里的活引用
2. **保留期内的 ops 里出现过的哈希**

第二条是有历史之后的必然结果——撤销删除时 blob 必须还在。

**但必须分清两件事，否则会和"ops 是唯一真相"直接冲突：**

> **保留期是 blob 的保护期，不是 op 的存活期。op 行永不删除。**

过了保留期，老的 op 不再保护它引用的 blob，blob 可被回收；但**那条 op 行还在**——历史里依然看得到"2019-03-01 删除了 50 个文件"，只是点进去没有内容（对应 2.4 里的"标注内容已过保留期"）。

如果 op 行真被删掉，`kist rebuild` 就重建不出当前状态，2.1 那条不变量立刻崩塌。

代价是 `ops` 表只增不减。量化一下：多数 op 的 payload 很小，批量 op 大些（500 个 UUID 约 8–18 KB），一百万条 op 平均 500 字节 ≈ 500 MB。对一个动辄几百 GB 的照片库，这是**完整历史的合理标价**。

三条安全措施：

- **`kist gc --dry-run` 是默认行为**，显示"将永久删除 N 个文件、释放 X GB"，要显式 `--yes` 才真删
- **宽限期**：不回收最近 24 小时内创建的 blob，挡住"blob 写完但事务未提交"的竞态
- **GC 期间持库锁**，与导入互斥

同时清理 `blobs/tmp/` 下超过 N 小时的孤儿临时文件。

这是系统里**唯一**真正销毁数据的地方，值得为它多写保护。

### 3.10 BlobStore 接口

```go
type BlobStore interface {
    Put(ctx context.Context, r io.Reader) (PutResult, error)   // 内容寻址，幂等
    Get(ctx context.Context, k Key) (io.ReadSeekCloser, error)
    Stat(ctx context.Context, k Key) (Info, error)
    Delete(ctx context.Context, k Key) error
    LocalPath(k Key) (string, bool)                            // ★ 关键逃生舱
}

type PutResult struct {
    Info                // Key + Size
    Outcome Outcome     // stored / deduped / repaired / collided
}
```

**`Put` 返回 `PutResult` 而不是裸 key。** 调用方必须能区分四种结果——新存入 / 去重命中 / 修复了一个损坏的 blob / 撞上真碰撞（3.3 那四条分支）。前两个是导入摘要要报的数字（"1200 个文件，340 个去重命中"），后两个是要高声告警的事件。它们都不是错误，塞进 `error` 语义不对；再开第二个方法则会让远端实现也被迫实现两遍。

`LocalPath` 是要点：**链接农场只对本地 blob 成立**。blob 被搬到 S3 冷层后，`boxes/` 下那个位置放什么？这是 v0.2 的真问题——将来放一个 `.kist-stub` 占位文件（记录哈希和大小），双击触发回热。v0.1 全本地，碰不到，但设计上不能挡住它。

v0.1 有两个「实现」：本地库、远端目录（修复源）。但它们是同一个 `blob.Dir` 指向两个地方，不是两个类型——理由和代价见 3.8「远端不是第二个类型」。

### 3.11 备份

因为 blob **不可变且内容寻址**，`rsync blobs/` 永远是安全的——没有部分写入、没有原地修改、增量永远最小。而 `boxes/` 完全不用备份：

```bash
rsync -a --exclude boxes/ --exclude derived/ ~/kist/ /backup/kist/
```

唯一需要小心的是 SQLite：运行中直接拷文件可能拿到不一致快照。提供 `kist backup <dest>`，内部用 `VACUUM INTO` 拿一致性快照再同步 blob。

**库在 SMB / NFS 上要告警**——SQLite 在网络文件系统上的锁语义不可靠，是数据损坏的经典成因。2.7 那把 `kist.lock` 上的咨询锁在 NFS 上同样不可靠，**结论一致、不新增限制**，但它落在这条警告的覆盖范围之内：躲开 SQLite 不等于躲开问题。

### 3.12 ID 方案

- **实体 ID（box / file / tag）用 UUIDv7**：随机但按时间有序，索引局部性好。不用自增整数，因为将来多设备同步时自增 ID 必然冲突——现在零成本，将来省一次痛苦迁移
- **op ID 用单调递增 int64**：它就是版本号，必须严格有序。将来同步时扩成 `(instance_id, seq)`

## 4. 数据访问层与查询

### 4.1 为什么要抽象，以及抽象的陷阱

要能支持 SQLite 和 Postgres 两种后端。但**抽象到最小公分母会把检索能力阉掉**，而检索恰恰是 kist 的核心卖点。

> **v0.1 只实现 SQLite。** Postgres 的接口、conformance suite、以及 4.7 那些语义约束都就位，但不写第二个实现——见 4.7 关于风险与缓解。

**正确的抽象方式不是"包一层通用 SQL"，而是接口里不出现 SQL，只出现领域语义。** 复杂查询用一个结构化的 `Query` 描述，由各实现自己翻译成它最擅长的形式。

### 4.2 Query AST

```go
type Query struct {
    Boxes  []BoxID
    Tags   TagExpr        // AND/OR/NOT 树
    Time   *DateRange     // box 时间范围 或 文件拍摄时间
    Kinds  []MediaKind    // image / video / document / …
    Text   string         // 文件名 / box 名 / 备注
    Sort   SortSpec       // 拍摄时间 | 导入时间 | 文件名 | 大小
    Cursor string         // keyset 分页
    Limit  int
}
```

**conformance test suite 围着这个结构写**——同一批 Query、同一批断言，任何实现跑出来必须结果一致。

它是 DAL 的**契约**，不是"跑在两个引擎上"的测试工具。**v0.1 只对 SQLite 跑，但套件本身照写不误**——将来 Postgres 落地时它就是现成的验收标准。这部分工作量不该省。

#### 4.2.1 v0.1 实际实现的 `Query`（M2b 定）

上面那个结构是写给 v0.1 全程的。落地时四个字段各有各的问题，逐条定死如下——**两把尺子贯穿这四条**：不能让 `verify --deep` 变成噪音（3.8），不能为了看起来更正确而破坏索引（4.5.1）。

```go
type Query struct {
    Boxes   []BoxID
    Folder  *FolderID
    Tags    TagExpr        // AND / OR / NOT 树
    Time    *DateRange     // 区间重叠
    Text    string
    Sort    SortSpec       // captured | imported | name
    Cursor  string
    Limit   int
}
```

`Kinds` 不在里面。

##### `Kinds` 砍掉，M3 跟提取管线一起落地

**它是四个字段里唯一一个连数据都没有的**：schema 里没有 kind 列，代码里没有这个概念，而 1.7 说 v0.1 的 metadata 只有 `file:size` / `file:mtime`。

否掉的两条路：

- **加一列，在导入时从扩展名算。** `kind` 可以从 `name` 纯函数地推出来，`name` 就在 payload 里，所以 `Apply` 保持纯（不变量 3 不破）。**但扩展名映射表是跟着二进制走的**：改一次映射表，`kist rebuild` 就重放出一个不同的库，`verify --deep` 当场报 `ViewDrift`。M2a 刚把不变量 1 变成用户能跑的检查，第一个新功能就让它在每次升级后变红——这个代价不能付
- **查询时从扩展名现算。** 不碰 schema、不碰 `Apply`，上面那个问题没有了，而且 4.4 已经认了 v0.1 全扫，再加一个不走索引的筛选不多花什么。真正的问题是**扩展名不是 kind**：一个 `.jpg` 里装着 PDF、一个没有扩展名的视频，这个字段就在撒谎。而 M3 的提取管线拿到的是真 kind，那时要么改掉一个 conformance suite 已经围着写死的字段语义，要么将错就错

所以 **conformance suite 在 v0.1 不覆盖 `Kinds`**。这一点要说出来，而不是假装契约是完整的。

##### `Tags` 真做成 AND / OR / NOT 树

4.3 已经定了「AST 支持嵌套，但 v0.1 的 UI 只暴露多 tag 取交集 + 一个排除列表」，所以问题只是 AST 那边做不做。**做。**

翻译成嵌套的 `EXISTS` 大约六十行，而这恰恰是「契约」两个字有意义的地方——将来 Postgres 实现必须在嵌套上也一致。**没有 UI 反而正是 conformance suite 存在的理由**：它是这条路径唯一的行使者。留到以后加等于改契约，而套件是围着契约写的。

##### `Sort` 做三个，`size` 砍掉

| 排序键 | 靠什么 |
|---|---|
| `captured` | `files(captured_at DESC, id DESC)`，`NULLS LAST`（4.5.1） |
| `imported` | 就是 `id`。UUIDv7 白给（4.5.1），`files(box_id, id)` 已经在 |
| `name` | `files(name_fold)`，字节序（4.8） |

`size` 是唯一一个要 join `blobs` 的，而且**没有任何索引能支撑 `ORDER BY b.size`**，必然退化成临时 B-tree——4.5 的 keyset 前提就没了。这和 4.5.1 否掉 `COALESCE` 是同一笔账。

将来真要，答案是**把 `size` 冗余到 `files`**（值本来就在导入 payload 的 `ImportedFile` 里，所以 `Apply` 依然是纯的，而且不像 `kind`，size 是事实不是猜测），不是 join。

##### 游标必须带排序标识

B1 那条「排序键换了，旧游标必须失效而不是给出错乱结果」到这里落地：

```
cursor = base64(sortID ␀ sortKey ␀ id)
```

请求的排序和游标里的对不上就**报错**，不是尽力而为。这是能测的：用 A 排序翻一页，拿那个游标去请求 B 排序，必须失败而不是返回乱序结果。

##### `Time` 取区间重叠，排序保持字节序

变精度日期本来就是**区间**：`2019` 就是 `[2019-01-01, 2019-12-31]`（1.3）。

**筛选取重叠，不取包含。** 找「2019 年春天」时，一个只知道是「2019 年」的 box 应该出来——它可能就是。对一个用途是「把东西找出来」的归档，**多给几个胜过漏掉**。而且因为存的是 ISO-8601 前缀，字符串比较就够：

```sql
WHERE value <= :hi AND value >= substr(:lo, 1, length(value))
```

右边那半是「这个值的区间结束时间 ≥ 范围起点」——只比 `:lo` 的前 `length(value)` 个字符，因为值是前缀。两个引擎都有 `substr` / `length`。不 sargable，但 4.4 已经认了 v0.1 全扫。

**排序不用动，前缀字典序就是对的。** `2019` < `2019-01` < `2019-01-01` 翻译过来是**「按区间起点排，粗的在前」**——一条能讲清楚的规则，零代码、零 schema、不破坏索引。

否掉的一条：**让 `2019` 按「年中」排**。那要算一个排序键，索引就没了，和 4.5.1 否掉 `COALESCE` 是同一笔账。

**`Time` 作用在哪**：文件查询看 `captured_at`，box 查询看 `start_at` / `end_at`；`captured_at` 为 NULL 的文件**不进**时间筛选结果。直接后果是 **M3 之前任何带时间筛选的文件查询都返回空**——这是对的，因为「没有文件有已知拍摄时间」就是事实。conformance suite 靠直接写 `captured_at` 的 fixture 来测，所以套件是真的，尽管产品数据还没有。

### 4.3 tag 筛选语义

**选中一个 tag 默认包含其所有后代**（选 `人物` 应该出来所有人的照片），可选"仅精确匹配"。

查询分两步：

```
第 1 步：内存树遍历，解析后代 ID 集合   →  [t1, t2, t3, …]
第 2 步：SELECT file_id FROM file_tags WHERE tag_id IN (t1,t2,t3,…)
```

**不需要闭包表**（把祖先 tag 冗余存到 `file_tags` 上）。闭包表读更快，但会让 tag 移动变成一次全库重写。既然 tag 树本来就在内存里，第一步几乎免费。实测发现慢了再上闭包表——数据模型不用改，是纯粹的加索引。

组合逻辑用 `EXISTS` 逐条件叠加：

```sql
SELECT f.* FROM files f
WHERE EXISTS (SELECT 1 FROM file_tags WHERE file_id=f.id AND tag_id IN (…人物/爸…))
  AND EXISTS (SELECT 1 FROM file_tags WHERE file_id=f.id AND tag_id IN (…地点/云南…))
  AND NOT EXISTS (SELECT 1 FROM file_tags WHERE file_id=f.id AND tag_id IN (…隐私…))
```

AST 支持 AND / OR / NOT 嵌套，但 **v0.1 的 UI 只暴露"多个 tag 取交集 + 一个排除列表"**。查询语言留到有人要。

**IN 列表上限：** 实测 SQLite `MAX_VARIABLE_NUMBER=32766`。tag 树几千个节点，撑死几千个参数，安全边界内。

### 4.4 检索：v0.1 用 LIKE 全扫

`Query.Text` 覆盖**文件名、box 名、备注**。不含 metadata（v0.2），不含 tag 名（走内存树匹配）。

实现就是 `LIKE '%关键词%'`，靠 `files(name)` 上的覆盖索引做索引扫描而非全表扫描（需用 `EXPLAIN QUERY PLAN` 验证实际走了覆盖索引）。

**为什么不做倒排索引。** 文件名和备注的文本量很小——文件名平均二三十字符，备注大多是空的，一百万文件加起来也就三十兆文本。实测 50 万行全扫 66ms，百万行窄表估计 60–100ms，对个人归档配上防抖完全够用。

而做索引要付的代价不小：分词包 + 固定用例测试、两套索引表、索引版本号 + 自动重建、约 70MB 磁盘，**以及这套设计里最脆弱的一处——索引侧和查询侧必须用同一个分词函数，一旦漂移就是"搜不到但不报错"**。

关键在于**这整块被 DAL 完全挡住了**，`Query.Text` 的语义不变，上层一行不用动。今天全扫，明天换倒排，是纯粹的实现替换。

**触发条件：** 单库超过 20 万文件，或接入 OCR（文本量涨两个数量级）。届时应当评估通用方案（sqlite-vec / pgvector 向量检索、外部搜索引擎），而不是手工 n-gram——那更可能是语义搜索而非子串匹配，`Query` 上加的字段都不一样。

#### 本项目自己的库上实测（M2b 收尾，4000 文件 / 5 MB 的 `kist.db`，macOS + NVMe）

上面那个「50 万行全扫 66ms」是别处量的。自己的库上量下来是这样：

| | 端到端耗时 |
|---|---|
| `kist version`（进程启动的地板） | **22 ms** |
| `find --name IMG_1 -n 1` | 19 ms |
| `find --name IMG_1 -n 1000` | 19 ms |
| `find --name IMG_1 --tag 人物 --sort name --asc -n 1000` | 19 ms |
| `ls`（一个目录 200 个文件） | 19 ms |

**结论是这个规模上查询本身量不出来——全部成本是进程启动。** 换页大小从 1 到 1000 没有差别，加 tag 条件、加文本、换排序也没有差别。

这不是「很快」，是「太小了，测不出东西」。有价值的部分是它**排除**了一件事：4.4 认下的「v0.1 全扫」在四千个文件上完全不构成问题，所以那条 20 万文件的触发条件不必提前。真正要量的是十万级的库，而那要等有人真的往里塞十万个文件。

### 4.5 分页用 keyset

照片网格要滚过十万张，`OFFSET 50000` 会让数据库扫掉前五万行。

```
cursor = base64(sort_key, id)
WHERE (sort_key, id) < (:key, :id) ORDER BY sort_key DESC, id DESC LIMIT 100
```

`id` 是必须的 tie-breaker，否则相同拍摄时间的照片会在翻页时重复或丢失。

#### 4.5.1 `captured_at` 为空的文件排在哪

没有 EXIF 的 PDF、扫描件、录音都没有 `captured_at`。**它们排最后，`ORDER BY captured_at DESC NULLS LAST, id DESC`。**

看上去更"正确"的做法是回退到另一个时间——`COALESCE(captured_at, created_at)`。**否掉它的不是语义，是索引。** 实测（SQLite 3.51）：

| ORDER BY | 查询计划 |
|---|---|
| `captured_at DESC NULLS LAST, id DESC` | `SCAN files USING COVERING INDEX files_captured` |
| `COALESCE(captured_at, created_at) DESC, id DESC` | 走索引取数，然后 **`USE TEMP B-TREE FOR ORDER BY`** |

也就是说任何 `COALESCE` 变体都会退化成全表临时排序，4.5 那套 keyset 分页的前提直接没了。要救回来只能加表达式索引或物化一个 `sort_at` 列，两条都要付存储与维护成本。

**而这个成本根本不用付，因为 `id` 已经免费给了同样的结果。** `id` 是 UUIDv7，时间戳内嵌在高位，且 ID 是在生成 op 时铸造的（不变量 3）——所以 `id DESC` **本身就是 `created_at DESC`**。tie-breaker 顺手把回退语义办了。

`captured_at` 还有一层语义问题，一并记在这里：它是**变精度的本地墙上时间**（1.3），`created_at` 是 **UTC 时间戳**。把两者 `COALESCE` 进同一个排序，等于把两条不同时间轴上的值放在一起比大小，误差可达 ±14 小时且不可见。这是"看上去更正确"的做法其实更不正确的地方。

> **M3 之前没有任何文件有 `captured_at`**（EXIF 提取是 M3），所以现在整列都是 NULL，实际排序结果就是纯 `id DESC`。这条决定因此是零成本的，且不锁死 M3 拿到真实数据后的选择。

### 4.6 索引清单

```sql
file_tags(tag_id, file_id)          -- 倒排，tag 筛选主力
file_tags(file_id, tag_id)          -- 正排，查某文件的所有 tag
box_tags(tag_id, box_id)            -- 同上，box 侧（见 1.6.1）
box_tags(box_id, tag_id)
files(folder_id, name)              -- UNIQUE，同时服务目录内浏览
files(box_id, id)                   -- Query.Boxes 筛选（box_id 是冗余列，见 1.5）
folders(parent_id, name) WHERE parent_id IS NOT NULL   -- UNIQUE，兼服务树形展开
folders(box_id)          WHERE parent_id IS NULL       -- UNIQUE，每 box 一个根（见 1.4）
folders(box_id)                     -- 列出一个 box 的全部目录
files(captured_at DESC, id DESC)    -- keyset 分页主排序（NULLS LAST，见 4.5.1）
files(name_fold)                    -- 文件名 LIKE 的覆盖索引（折叠列，见 4.7）
files(blob_key)                     -- GC 的引用计数
blobs(sha256)                       -- 去重查重，非唯一（碰撞时多行，见 3.3）
tags(name_fold)                     -- UNIQUE，全局唯一 + 名称查找（见 1.6）
tags(parent_id)                     -- 树形展开
tag_rejections(file_id, tag_id)     -- 提取器写入前的抑制名单查询
metadata(target_type, target_id, key)  -- 主键
ops(id)                             -- 主键即版本号
ops(reverts_id) WHERE NOT NULL      -- 历史面板判断"是否已被撤销"
op_boxes(box_id, op_id DESC)        -- 按 box 查历史
op_files(file_id, op_id DESC)       -- 单个文件的完整历史
```

**`op_boxes` / `op_files` 不对 `boxes` / `files` 建外键。** box 被删掉之后它的历史必须还在——那正是回收站和撤销的来源。它们只对 `ops(id)` 建外键。

### 4.7 引擎语义分歧：v0.1 就要遵守的设计约束

**推迟 Postgres 实现要认的风险是：抽象只有在有第二个实现时才算被验证过。**

缓解办法几乎零成本——**把语义决定权拿到 Go 里，而不是依赖引擎的默认行为**：

> **Go 拥有表示形式；DB 只存两个引擎解释一致的原始类型，只做字节比较。**

最要命的一条是 **`LIKE` 大小写**，因为 v0.1 的搜索完全建立在 LIKE 上。如果 SQLite 实现直接依赖引擎默认行为，将来接 Postgres 时搜索行为会**静默改变**。做法（与 6.2 里 bigramize 的思路同源）：

- 写入时由 Go 生成一个折叠列（`strings.ToLower` + NFC 规范化）
- 查询时把模式串用**同一个函数**处理后匹配折叠列
- 数据库只做字节比较，两个引擎行为必然相同

顺带这也定死了"搜索是否区分大小写"这个产品问题——**不区分，而且是我们说了算，不是引擎替我们决定**。

完整清单：

| 分歧 | 说明 |
|---|---|
| **`LIKE` 大小写** | SQLite 对 ASCII 默认**不**区分大小写，Postgres **区分**。而 v0.1 的搜索完全建立在 LIKE 上——这一条晚发现就是全局返工 |
| 时间戳类型映射 | SQLite 无原生类型，Postgres 有 `timestamptz` / `timestamp`。同上：Go 拥有表示形式，DB 存两边一致的原始类型 |
| upsert 语法 | `ON CONFLICT` 细节不同 |
| 排序规则 | 中文排序在两边表现不同。**v0.1 的决定见 4.8：一律字节序，Postgres 实现必须显式写 `COLLATE "C"`** |
| **`NULL` 的排序位置** | SQLite 视 `NULL` 为最小值，`DESC` 时天然排最后；**Postgres 的 `DESC` 默认是 `NULLS FIRST`**。所以凡是可空列的排序都**必须显式写 `NULLS LAST`**（见 4.5.1）。**M2b 更正：不是「本地永远测不出来」，是 `DESC` 方向测不出来。** `ASC` 方向 SQLite 默认把 NULL 排在最前，所以只要契约同时提供升序，显式的 `NULLS LAST` 在 SQLite 上就是承重的、可以被测出来的——实测把它去掉，`captured:desc` 全绿而 `captured:asc` 当场红。这是「凡引擎语义可能不同的地方，决定权拿到 Go 里」这条缓解办法第一次在本地拿到证据 |
| 布尔值 | SQLite 用 0/1 |
| JSON 函数 | 名称与行为有差异 |

### 4.8 排序语义：v0.1 用字节序

**决定：v0.1 全部排序用 UTF-8 字节序（即码点序），不引入任何 locale 相关的排序。** Postgres 实现落地时要显式写 `ORDER BY … COLLATE "C"`，否则它会跟着数据库 collation 走，与 SQLite 静默分叉。

这条决定建立在一轮实测上（2026-08-26，darwin/arm64），因为直觉在这里靠不住。测试字集选的是能把三种排法完全区分开的七个字：

| 字 | 码点 | 拼音 | 笔画 |
|---|---|---|---|
| 阿 | U+963F | a | 7 |
| 陈 | U+9648 | chen | 7 |
| 李 | U+674E | li | 7 |
| 王 | U+738B | wang | 4 |
| 一 | U+4E00 | yi | 1 |
| 张 | U+5F20 | zhang | 7 |
| 重 | U+91CD | chong / zhong | 9 |

**发现一：不存在"中文的正确顺序"，它是 locale 的函数。**

| locale | 顺序 | 是什么 |
|---|---|---|
| `zh-Hans` | 阿 陈 李 王 一 张 重 | 拼音 |
| `zh-Hant` | 一 王 张 李 阿 陈 重 | 笔画 |
| `en` / `C` | 一 张 李 王 重 阿 陈 | 码点 |

**macOS 实测**：Finder 用的 `localizedStandardCompare`、`ls` 用的 `strcoll`、以及 Go 的 `x/text/collate`，在这三个 locale 下给出**逐字相同**的结果——因为用的都是 CLDR/UCA 数据。

**Linux 实测**（Debian bookworm，glibc 2.36，容器内 `locale-gen` 后 `ls`）：

```
C.UTF-8       一 张 李 王 重 阿 陈      码点
en_US.UTF-8   一 张 李 王 重 阿 陈      码点
zh_CN.UTF-8   阿 陈 李 王 一 张 重      拼音，与 macOS 一致
```

⚠️ 但要注意**这个结论依赖 `zh_CN.UTF-8` 真的被生成过**。第一次测试时 `locales` 包没装上、locale 静默退回 C，三个 locale 给出了完全相同的码点序——一个看起来很像结论的假象。桌面发行版默认装了中文 locale，容器和服务器常常没有。

**Windows 未实测。** 据文档是同样的形状：资源管理器走 `StrCmpLogicalW` → `CompareString`，跟用户 locale（zh-CN 默认读音序，zh-TW 默认笔画序，非 CJK locale 码点序）。将来若要依赖请先验证。

**"跟随平台"因此不是一个能稳定兑现的承诺**：同一批文件在同一台机器上，`ls` 和 Finder 可能不同（前者看 `LC_COLLATE`，后者看用户语言设置），容器里和桌面上也可能不同。字节序至少是四个平台、两个引擎、任意时间都相同的那一个。

**发现二：码点序不是乱序，是部首笔画序。** CJK 基本区 U+4E00–9FFF 按《康熙字典》部首、部首内按笔画编码，所以同部首的字在码点上紧密聚集：

| | 码点跨度 |
|---|---|
| 阜部 阳阴阿陆陈险陶隆随 | 92 |
| 木部 李杨松林柳样桥梅 | 311 |
| 水部 江汪河洋流海清湖 | 503 |
| 随机 9 个常用字 | 16847 |

也就是说字节序对应的是一种**真实的传统字典序**，只是不是现代人对文件名排序的期待。这一点推翻了"码点序对中文毫无意义所以必须做拼音"的论证。

**发现三：SQLite 只有 BINARY / NOCASE / RTRIM 三个 collation**，`NOCASE` 只折叠 ASCII 的 A–Z，对中文完全不起作用；`COLLATE zh_CN` 一类的 ICU 名字直接报 `no such collation sequence`——纯 Go 驱动没有编入 ICU 扩展。

**这条决定由测试执行，不只是文字。** `internal/store/collation_test.go` 用上表那七个字断言 `ORDER BY name` 的结果必须是字节序、且**必须不是**拼音序，并断言这个 build 只注册了 `BINARY` / `NOCASE` / `RTRIM` 三个内置 collation。CI 在 Linux / macOS / Windows 三个平台上跑它——三平台一致本身就是选字节序的理由，所以那个一致性也该被验证而不是被假设。

#### 否掉的两条路

**❌ 在 SQLite 里注册 Go 实现的 collation。** `modernc.org/sqlite` 提供 `RegisterCollationUtf8`，把 `x/text/collate` 接上去确实能得到拼音序，索引也能建、能走覆盖索引。两条否掉的理由：

1. **它让标准工具打不开这个库。** 实测：用系统 `sqlite3` CLI 打开带 `COLLATE PINYIN` 索引的库，`SELECT *` 正常，但 `ORDER BY name` 报 `no such collation sequence`，**`PRAGMA integrity_check` 一样报错**。对一个 M2 整个里程碑叫「完整性与可恢复」、且承诺"数据比软件活得久"的项目，用户拿不了标准工具自查自己的归档，这是否决票
2. **它保证不了跨引擎一致。** SQLite 侧的排序来自 `x/text` 打包的 CLDR 数据，Postgres 侧来自系统 libicu，两个版本不同就静默分叉——正是 4.7 要防的那类问题

**❌ 现在就加 Go 生成的排序键列。** 这条路技术上是干净的（见下面的逃生舱），但 v0.1 不需要付这个成本：实测平均 104 字节/行，100 万文件的库多约 200 MB（列 + 索引），而 v0.1 的主排序本来就是时间（4.6 里那条 keyset 索引是 `files(captured_at DESC, id DESC)`），文件名只是四个排序选项之一。**等有用户、有需求再做。**

#### 逃生舱：Go 生成的排序键列

触发条件：**有用户实际抱怨排序顺序**。届时的做法（已验证可行，不改数据模型）：

- `boxes` / `folders` / `files` 加 `name_sort BLOB`，值由 `x/text/collate` 的 `KeyFromString` 生成，DB 只做字节比较——这正是 4.7 那条原则的形状，两个引擎不可能分叉，CLDR 版本由 `go.mod` 钉死
- locale 成为库级配置（`kist.toml` 的 `[storage] collation`），`init` 时探测、和链接方式一起摊在确认页上
- 改 locale = 全表重算这一列。**实测 20 万行 2.46 秒，外推 100 万行约 12 秒**；不需要 `REINDEX`（普通列上的普通索引，`UPDATE` 时自己跟着变）；中途失败重跑即可，因为 `name_sort` 是派生列，权威数据只有 `ops` + `blobs/`（不变量 1）
- **keyset 游标必须编入 collation 代次**，排序键换了旧游标要被拒绝而不是照算出错乱结果
- ⚠️ 届时要给不变量 3 开一条明确的例外：`name_sort` 不能进 payload（否则改 locale 就要改写 append-only 的历史），只能在 `Apply` 里算，于是 `Apply` 从「payload 的纯函数」变成「(payload, 库级 collation 配置) 的纯函数」。库级配置对一次重放全程恒定，重放依然确定性，但这条要写下来。`name_fold` 其实早就是这个形状，只是 `Fold()` 不带参数所以没暴露

**对比另一条路：依赖引擎 collation 时同样的重算会发生，只是由操作系统替你触发。** Postgres 有 `collversion` 字段，系统 libicu 或 glibc 一升级就报 `collation version mismatch … indexes may be corrupt`，是 Postgres 运维里的经典事故。区别不在于要不要重算，而在于**重算是你按下的，还是某天 `apt upgrade` 之后静默出错**。

## 5. 技术选型

### 5.1 后端

**不用 Web 框架。** Go 1.22 起 `net/http` 的 `ServeMux` 支持方法 + 路径参数（`GET /api/boxes/{id}`），三四十个端点的 JSON API 完全够用。gin / echo 会引入自己的 `Context` 类型污染整个 handler 层；fiber 基于 fasthttp，脱离 `net/http` 生态，不考虑。

**但 API 契约要一层：[Huma v2](https://github.com/danielgtaylor/huma)。** handler 的入参出参是带 tag 的 Go struct，自动生成 OpenAPI 3.1，跑在标准 `ServeMux` 之上（不是另一套运行时，随时能退回纯 stdlib）。

理由不是省代码，而是**这个 API 不只给自家前端用**——未来的手机 app 要用、第三方集成要用、自部署用户会拿它写脚本。契约漂移的代价很高，而手机 app 和第三方客户端可以直接从 spec 生成。它只在 `api` 包里，不碰 `domain` / `library`。如果实际做起来觉得重，退回 stdlib + 自写 JSON 编解码辅助即可。

| 用途 | 选择 | 说明 |
|---|---|---|
| SQLite 驱动 | `modernc.org/sqlite` | 纯 Go，已实测（见 6.1） |
| Postgres 驱动 | `jackc/pgx/v5` | 事实标准。**v0.2 才用到** |
| SQL 层 | **`sqlc`** | 从 SQL 生成类型安全的 Go，**正好契合本设计**——SQL 是一等公民、每个方言写自己最优的查询 |
| 迁移 | `pressly/goose` | 简单，可 embed |
| CLI | `spf13/cobra` | 事实标准 |
| 配置 | `BurntSushi/toml` | 不用 viper，太重 |
| 日志 | `log/slog` | 标准库 |
| UUIDv7 | `google/uuid` v1.6+ | |
| 图像处理 | `disintegration/imaging` | 纯 Go，缩略图在个人规模够用，不引 libvips（CGO） |

**明确不要 ORM（GORM / ent）。** 它们会强推统一 SQL，把第 4 节 DAL 设计的意义整个抹掉——那个设计的核心正是"接口里不出现 SQL，各实现写自己最优的查询"。

### 5.2 Web UI

**React + TypeScript + Vite**，构建产物 `go:embed` 进二进制。

选 React 不是因为技术上最优，而是因为**开源项目的贡献者池最大**。Svelte（Immich 用）和 Vue（PhotoPrism 用）都没有强到能压倒这一点。

kist 的几个硬需求，React 生态恰好最成熟：

| 需求 | 库 |
|---|---|
| 上万张图的虚拟滚动网格 | `@tanstack/react-virtual` |
| keyset 分页 + 缓存 + 乐观更新 | `@tanstack/react-query`（与 4.5 的游标分页 API 契合） |
| 拖拽上传 + 进度 | `react-dropzone` |
| tag 树组件 | 自己写 |

**样式用 Tailwind + 无头组件（Radix 一类），不用 Ant Design / MUI。** 重型组件库会让 kist 长得跟所有后台管理系统一样，且 bundle 大到不适合 embed。照片应用的界面应该让位给内容。

### 5.3 HEIC 与 ffmpeg：单二进制的唯一裂缝

`imaging` 和 Go 标准库**都不支持 HEIC**。而 iPhone 默认拍出来就是 HEIC——对个人照片归档来说这是主流情况，不是边角情况。

能解码 HEIC 的只有两条路，都是外部依赖：`libheif`（CGO）或 **ffmpeg**。视频转码同理。

**倾向方案：检测到系统 ffmpeg 就启用，检测不到则降级并明确告知用户**（没有 ffmpeg 也能存能搜，只是没有 HEIC 缩略图和视频预览），同时提供一个带 ffmpeg 的完整发行版给不想折腾的用户。单二进制的承诺因此保住——它只影响派生媒体，不影响核心功能。

M3 开始前需最终确认，见第 9 节。

### 5.4 手机端

**现在不选，但决策点想清楚。** 手机端有两个需求，对技术的要求差一个数量级：

| 需求 | 需要什么 |
|---|---|
| 浏览归档 | 一个响应式网页就够 |
| **自动备份手机相册** | 相册库权限、后台上传、断点续传、系统级调度 |

第一个做成 **PWA 几乎零成本**（响应式 + manifest + 离线壳），第二个在 iOS 上 PWA **根本做不到**（没有后台同步、没有相册库访问）。

路径：

1. 先把 Web UI 做成合格的 PWA，覆盖"在手机上翻自己的归档"
2. 等自动备份成为优先级时，再做原生 app。届时的选择：**React Native + Expo**（与 Web 端共享 TypeScript 类型和 OpenAPI 生成的客户端，贡献者池重叠）或 **Flutter**（app 质量更好，Immich 正是为了后台备份选的它，但 Dart 会把代码库和贡献者池劈成两半）。倾向 React Native，但这个决定取决于那时是否有人愿意维护第二套代码

**真正现在就要做对的是：API 从第一天起就是干净、有文档、有版本的 HTTP 接口。** 这是让任何客户端成为可能的前提，也是 5.1 里上 Huma 的根本原因。

## 6. 已验证的技术假设

以下结论来自 2026-08-22 在 darwin/arm64 上的实测（Go 1.26.1，`modernc.org/sqlite` v1.57.0）。

### 6.1 modernc.org/sqlite 可用性 ✅

```
SQLite version:  3.53.3
compile_options: ENABLE_FTS5 ✅   MAX_VARIABLE_NUMBER=32766
递归 CTE ✅   窗口函数 ✅   trigram 分词器 ✅
```

**纯 Go 驱动带完整 FTS5，单二进制的承诺站得住。** 选它而非 `mattn/go-sqlite3`（CGO）是因为交叉编译无障碍。

**与 C 实现的性能差距实测（2026-08-26，同一个 20 万行库文件）：**

| | modernc（纯 Go） | 系统 `sqlite3`（C 3.51） |
|---|---|---|
| 全表扫描 20 万行 | 22–35 ms | ~10 ms |
| 事务内插入 20 万行 | 0.32 s（63 万行/秒） | — |

**大约 2 倍慢，如实记下。** 但这不足以推翻选型，理由是换 C 版要付的代价买不到对应的好处：

- 交叉编译没了。现在 `release.yml` 在一台 ubuntu runner 上一次编出四个平台；上 cgo 要四台原生 runner 加每平台一套工具链
- 静态链接 ICU 之后二进制从约 15 MB 涨到约 50 MB
- 「下载一个文件就能跑」变成「装 Docker」。而二进制版和容器版行为若不同，比慢 2 倍糟糕得多
- **最关键的是它解决不了本来想解决的问题**：即使两边都用 ICU，我们打包的版本和用户 Postgres 服务器上的版本仍是两个版本，跨引擎一致性还是拿不到（见 4.8）

**重开这个决定的触发条件：需要自定义 FTS5 分词器。** 6.2 已经撞过这堵墙——`fts5_api` 是 C 接口，纯 Go 驱动接不上，所以中文分词只能用手切 bigram 的 hack。真要做正经的中文全文检索时，这个选型该连同 8 节里「全文倒排索引」那一条一起重新评估。

### 6.2 全文检索的探测结果（供将来参考）

v0.1 不用倒排索引，但这轮探测把未知项变成了已知项，记录下来：

**SQLite 内置分词器只有 `unicode61` / `ascii` / `porter` / `trigram`。** 没有 bigram，没有 icu，没有 jieba——自定义分词器要走 C 的 `fts5_api`，纯 Go 驱动接不上。

**`trigram` 的 3 字符是下限而非窗口：** 2 字查询 hits=0（且**不报错**，静默返回空），3 字及以上正常，9 字也正常。中文里两字词恰恰最常见（云南、护照、北京、体检、发票），所以 trigram 单独用不了。

**50 万行实测：**

| 查询 | trigram | 自切 bigram + unicode61 | 普通表 LIKE |
|---|---|---|---|
| `护照`（2 字） | **0 hits** ❌ | 1 hit, 0.09ms | 1 hit, 66ms |
| `护照扫`（3 字） | 1 hit, 0.05ms | 1 hit, 0.05ms | 1 hit, 97ms |
| 索引体积 | 74.3 MB | 71.9 MB | — |

「自切 bigram」指在 Go 里把中文切成二元组用空格连接后交给 `unicode61`。它能工作且体积更小，但是个手工 hack；真要做索引时应评估通用方案。

**另有一个反直觉的发现：** `LIKE '%签发地%'` 在 trigram 表上是 0.0ms（SQLite 会把 ≥3 确定字符的 LIKE 自动改写成查三元组索引），在普通表上是 96.6ms。

## 7. 里程碑

排序原则：**每个里程碑结束时都有能实际用上的东西。**

### M0 — 开源项目地基（很小）

LICENSE（Apache-2.0）、README 骨架、`AGENTS.md`、issue 模板、GitHub Actions。

验证单二进制在 darwin/arm64、darwin/amd64、linux/amd64、windows/amd64 上都能跑。

**CI 拆成两个 workflow：**

```
push / pull_request  →  build + test + vet        快，每次都跑
tag                  →  四平台交叉编译 + 产物      慢，只在发版
```

- **两种事件都监听**，尽管现在只有 push 会触发。将来仓库公开、切到 PR 流程时不用改 workflow
- **交叉编译只在 tag 上跑。** 每次提交跑四遍构建又慢又费额度，而四平台产物是发版才需要的
- **提供与 CI 等价的本地命令（`make check`）。** 对单人仓库，这比任何门禁都实用——推之前自己跑一遍，红叉根本不会出现

**CI workflow 内部再拆成两个 job：**

| job | 跑在 | 内容 |
|---|---|---|
| `check` | ubuntu | `make check`：tidy + gofmt + vet + `go test -race` + build |
| `platforms` | macos / windows | 只跑 `go test` + `go build` |

理由：**平台分叉的地方恰好是最凶的地方**——链接农场的能力探测（reflink/hardlink/symlink）、Windows 的路径长度与 `\\?\`、0444、fsync 与原子 rename。这些 bug 留到发版才发现太晚。

否掉的两条：

- **三平台各跑一遍 `make check`。** gofmt 和 `go mod tidy` 检查是平台无关的，跑三遍纯浪费；而且 GNU make 在 Windows runner 上不保证存在
- **把跨平台测试推到 release 门禁上**，以省 private 仓库 macOS runner 的 10 倍计费。开发频率低，额度不是瓶颈——不值得用"晚发现平台 bug"换这点钱

release workflow 里的 smoke job 与此**互补而非重复**：CI 测的是源码在本机编译的结果，smoke 跑的是**交叉编译出来、即将发给用户的那个二进制**，在它声称支持的平台上。四个 runner（`ubuntu-latest` / `macos-13` amd64 / `macos-latest` arm64 / `windows-latest`）恰好覆盖四个目标，所以"验证单二进制在四平台上都能跑"是自动的。

**cobra 在 M0 就引入**，而不是先手写一个 stdlib 的子命令分发器。stdlib 到 `flag` 这一层就没有子命令抽象了（`cmd/go` 自己也是手写 `Command` struct + `flag.FlagSet`），而 M1 反正要用 cobra，写一个 M1 就删的分发器是纯浪费。附带好处：go.sum 非空，CI 才真的验证了模块下载与缓存这条路。

**分支策略：开源之前直接在 `main` 上开发**，不开功能分支（探索性、可能整个扔掉的工作除外）。切换到 PR 流程的触发条件是**仓库公开**，而不是"CI 存在"——单人仓库里 CI 挂了自己 fix forward 就行，"main 永不损坏"在有别人拉 main 之前价值接近零。

### M1 — 内核闭环，无 UI（v0.1 的 30–40%）

- `domain` 类型
- `store` 接口 + **conformance test suite** + SQLite 实现
- `oplog`：op 定义、Apply、Inverse、反向重放
- `blob`：内容寻址、原子写、重新哈希校验、碰撞 `.1` 后缀
- `boxes/` 链接农场 + 能力探测
- `library`：唯一写入口
- CLI：`init` / `box new` / `tag` / `import --box` / `ls` / `find` / `file tag` / `relink`

**产出：能用命令行把真实数据塞进去、按 tag 和文件名筛出来。**

> `file tag` 是 M1c 补上的：产出那句写的是「按 **tag** 和文件名筛出来」，而 `file_tags` 在文件能被打 tag 之前一行都没有，`find --tag` 必然返回空。产出蕴含了它。

### M2 — 完整性与可恢复（~15%）

**拆成 M2a / M2b。** 原本这里是一个里程碑，写实现计划时发现它是两件事：前三项服务于「数据可信了」这个产出，第四项（conformance suite）不服务它，而且**它要求的东西大部分还不存在**。

#### M2a — 完整性（产出：数据可信了）

- `verify` / `verify --deep` / `scrub` / `repair` / `rebuild` 五个 CLI（分工见 3.8）
- `blobs/tmp/` 崩溃残留清理（阈值与时机见 3.9）
- 远端 blob 目录（本地目录 / 移动硬盘）+ 从远端修复
- ~~`gc`~~ 推迟（见 3.9），v0.1 不回收任何东西

> **实践建议：M2a 通过之前，别删掉导入源的原始副本。** M1 能塞数据，但要到 M2a 才有能力告诉你塞进去的东西有没有问题。

#### M2b — Query 契约（产出：DAL 的契约定死了）

- 4.2 的 `Query` AST 落地（新包 `internal/query`），`ls` / `find` 迁到它上面
- conformance test suite 写完（只对 SQLite 跑，见 4.2）
- CLI 增补：`find --sort` / `--asc` / `--since` / `--until`
- **`kist ls` 的默认排序从拍摄时间倒序改成文件名升序。** 目录浏览按拍摄时间倒序是反直觉的——`ls` 就该像 `ls`。`find` 保持拍摄时间倒序，因为检索结果的默认排序是「最近的先看」

**M2b 开写前要先定四件事**，它们是 4.2 那个结构与现状的差距，也是 `open-questions.md` B1 / B1c 的内容：

| 4.2 的字段 | 缺口 |
|---|---|
| `Tags TagExpr`（AND/OR/NOT 树） | 现在是扁平的 `AllOf` / `NoneOf`，CLI 也没有布尔语法 |
| `Kinds []MediaKind` | **schema 里没有 kind 列，代码里没有这个概念。** 1.7 说 v0.1 的 metadata 只有 `file:size` / `file:mtime`，而提取管线是 M3 |
| `Sort SortSpec`（拍摄 / 导入 / 文件名 / 大小） | keyset 游标写死了 `captured_at, id`；而 `size` 不在 `files` 上，它在 `blobs` 上 |
| `Time *DateRange` | 变精度日期怎么混排，B1 里明确没定 |

**为什么拆而不是硬着头皮一起做**：M2a 的规范（3.8 / 3.9 / 3.10）写得足够动手，M2b 要先开一轮设计。捆在一起的结果是「数据可信了」这个产出被一个设计问题挡住，而它恰恰是现在最该先交付的——M1 刚刚让人往库里塞了真实数据。

> **Postgres 实现整体推迟到 v0.2**（原计划在此加"行走骨架"）。代价是抽象在 v0.1 内得不到第二个实现的验证——缓解办法见 4.7：凡引擎语义可能不同的地方，决定权拿到 Go 里，不依赖引擎默认行为。

### M3 — 提取与派生（~15%）

- `extract` 管线（可插拔接口）+ EXIF / 文件固有属性 → metadata（**只做 extracted 侧**）
- 缩略图（同步）+ 预览图（懒生成）+ 视频转码队列
- `derived/` 布局、recipe 版本号、`generation_ms`

**产出：能按拍摄时间排序，网格浏览有图了。**

> **开始前需要定 5.3 那个问题：** HEIC 和视频都需要 ffmpeg 或 libheif，而 iPhone 照片默认就是 HEIC——这不是边角情况。

### M4 — Web UI（~20–30%）

HTTP JSON API + 前端产物 embed；box 列表/详情、拖拽上传、网格浏览、tag 树 + 筛选、文件预览。

**产出：第一次可以不用命令行。这是能给别人看的第一个版本。**

### M5 — 历史 UI（~15%）

op 历史面板、按 box 回溯、文件版本链对比、撤销（严格冲突校验）、从 ops 渲染的回收站、保留期配置 + GC 预览界面。

**产出："完整版本历史"这个差异化卖点兑现。**

### M6 — 收口

文档、打包、跨平台产物验证、v0.1 发布。（Postgres 实现已移出 v0.1，见第 8 节。）

## 10. 商业化路径备忘（非 v0.1 范围）

许可证选了 Apache-2.0，意味着护城河不在代码而在**运营**。可行的锚点：

- **身份中转**：微信网页授权登录需要服务号或开放平台网站应用，两者都要求企业主体资质——**个人开发者申请不到 AppID**。所以自部署用户不可能自己搞定微信登录。用官方主体的 OAuth 验证后签发 token 回用户的私有实例，是用户几乎不可能自建的能力
- **可达性**：NAT 打洞与中继（与 Tailscale 控制面同一个模型）
- **备份目标**：不是卖存储空间，而是**让 scrub 有东西可修**。这比跟 S3 拼单价的故事硬得多

不建议做"官方网盘后端"——那是在跟 S3 / OSS / B2 比单价，毛利薄，国内还要处理备案和内容合规。
